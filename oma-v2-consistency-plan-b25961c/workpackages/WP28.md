## 1. 이 작업이 필요한 이유와 판정의 강도

좋은 상태 모델도 UI가 저장/전송/수락/실행 완료를 같은 성공 표시로 보이면 사용자가 잘못된 결정을 한다. 이 작업은 새 디자인이 아니라 앞선 contracts를 사실대로 보여주는 표면의 일관성을 다룬다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP28.01 — 사용자에게 말하는 사실 목록

각 화면·notice가 무엇을 근거로 말하는지 표로 적는다. 저장 성공, 적용 대기, 전송 queue 수락, 엔진 수락, run settled, 배치 정산을 서로 구분한다. observation 시각과 reason은 끝까지 유지한다.

### WP28.02 — 설정/extension ports 이관

화면은 managed config owner에 edit intent만 전달한다. path 재해석/별도 JSON patch/revision 계산을 화면에 남기지 않는다. 미지원 편집은 확정 전에 알려주고 기존 값은 보존한다.

### WP28.03 — prompt와 mail

WP09의 prompt disposition을 한 번만 반영한다. queued text는 세션 종료 시 반환하지만 crash-recoverable draft store를 만들지 않은 상태에서 crash 후 복구를 약속하지 않는다. mail list의 read/unread view와 durable acknowledgement 의미를 구분한다.

### WP28.04 — 렌더링 bounds와 종료

입력 chunk, Unicode, JSON encoded size, transcript retention, pty raw mode/resize/정상 및 오류 종료를 확인한다. timeout/종료 시 오래된 observer가 새 화면 상태를 다시 덮지 않도록 한다.

### WP28.05 — 전체 TUI 파일 검토

view helpers까지 REVIEW-COVERAGE에서 실제 읽기 완료를 표시한다. 기존 순수 model/render를 유지하고 business authority를 렌더러에 넣지 않는다. 디자인 취향 때문에 protocol/wire/durable owner를 수정하지 않는다.

## 4. 회귀 시험 — production 경로를 사용한다

### V28A — TUI의 설정·실제 상태·메일 의미

**준비:** 새 config generation과 이전 활성 session, stale/missing/foreign status, 읽지 않은 mail

**동작:** 화면 전환·설정 확정·메일 조회·오류 통지를 실제 app/ports로 수행한다.

**관측해야 할 결과:** configured/committed/active가 구분되고 unknown이 0/idle로 바뀌지 않는다. mail을 표시했다는 이유만으로 batch presented/ack를 쓴다고 주장하지 않는다.

**음성 대조군:** 설정 저장 직후 활성 엔진 모델까지 바뀐 것처럼 표시하거나 파일 조회를 delivery 완료로 해석하면 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V28B — 터미널 입력·출력·복원 한도

**준비:** 실제 pty, 작은 터미널과 grapheme/멀티바이트 분할 입력, 대기 prompt 상한

**동작:** resize/종료/입력 중 오류/엔진 종료를 실행한다.

**관측해야 할 결과:** raw mode 복원·bounded transcript·UTF-8 encoded frame 제한·prompt 반환이 유지된다. 화면 폭 축소가 text 상태를 조용히 유실시키지 않는다.

**음성 대조군:** 문자 수만으로 frame 한도를 계산하거나 예외 경로에서 terminal restore를 누락하면 실패한다.

**lane / 현재 실행 상태:** `pty` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

unknown을 빈 값으로 성공 표시, UI refresh가 auth/settle 수행, pending prompt 무조건 재전송, 적용 안 된 model을 active로 표시, write failure 뒤 값만 낙관적으로 유지, 정합성 변경과 무관한 전체 UI 재작성은 금지한다.

## 6. 호환성·실패·롤백

C1/C2 field label와 표시 의미는 D05에 따른다. 기존 CLI/Public wire를 디자인 이유로 바꾸지 않는다. 한 세션의 텍스트 보호와 crash durability는 별개의 지원 범위다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

UI의 모든 성공/오류/대기 문구가 실제 phase에 연결된다. pty와 actual engine 결합 검증의 범위를 구분하고 unsupported 상태에서도 진단·입력 반환·터미널 복원이 일관된다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
