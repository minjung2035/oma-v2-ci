## 1. 이 작업이 필요한 이유와 판정의 강도

H05는 placeholder 생성 retry에 명시적 상한이 없는 구조에 대한 검토 항목이다. 실제 임의 provider 전체가 실패한다고 주장하지 않는다. engine SDK·session 저장·sandbox closure는 타입이나 helper 시험만으로 증명할 수 없으므로 잠긴 실제 엔진과 지원 환경을 따로 검증한다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP27.01 — pinned SDK 계약 확보

package-lock의 정확한 엔진 버전과 사용 SDK/CLI/event를 대응한다. 구현 AI는 해당 버전 source/공식 문서를 읽고 가정한 API와 실제 동작을 구분한다. refactor 편의를 위한 dependency upgrade를 같은 변경에 섞지 않는다.

### WP27.02 — receipt evidence 범위

extension이 boundary entry를 추가했다는 사실, RPC notification을 받았다는 사실, session 데이터가 OS/power loss에도 보존된다는 사실을 분리한다. 마지막 보장이 없으면 증거 부족을 명시하고 accepted=false/unknown 분기를 뭉개지 않는다. 세션 파일 형식의 별도 복제 parser는 꼭 필요할 때만 제한적으로 도입한다.

### WP27.03 — opaque relay 유지

목적지·연결 수·요청/응답 stream·timeout·자원 해제 계약을 검토한다. 가격/token/모델 response 의미를 OMA가 다시 해석하는 새 시스템을 만들지 않는다. 인증 정보는 기존 trusted transport의 수명 안에만 두고 test fixture에는 synthetic data를 사용한다.

### WP27.04 — placeholder 총함수

지원 credential shape에서 유한 횟수의 후보 생성/검증으로 끝나게 한다. 반복 실패는 existing unsupported 오류로 거절한다. 랜덤성을 신뢰 보장이나 종료 증명으로 사용하지 않는다. 실제 token/prefix 형태를 새로 수집하거나 저장하지 않는다.

### WP27.05 — extension/containment 회귀

core extension closure와 mount·workspace guard·tool surface를 따로 검토한다. tool 비활성화는 OS 권한 봉쇄가 아니다. rootfs="/"의 기존 명시적 opt-out은 은밀히 제거하지 않고 지원표에서 unconfined로 분리한다. 동등성 시험 없이 경계를 가로질러 runtime import를 추가하지 않는다.

## 4. 회귀 시험 — production 경로를 사용한다

### V27A — 동봉 엔진과 trusted extension의 실제 계약

**준비:** 잠긴 dependency의 실제 Pi engine, production spawn plan과 추가 검토된 test extension, credentials 없는 local fixture

**동작:** 로드/등록/session_start/tool surface/delivery response/agent_settled/종료 순서를 관측한다.

**관측해야 할 결과:** 가짜 SDK fixture의 성공이 아니라 실제 엔진에서 core extension이 로드되고 기대된 이벤트가 확인된다. boundary 관측과 session 파일 durability의 증거를 분리한다.

**음성 대조군:** 지원되지 않는 로드 시점 API 사용 또는 fake event만으로 경계가 확인됐다고 처리하는 control이 실패한다.

**lane / 현재 실행 상태:** `engine` / `NOT_RUN`.
### V27B — Relay·placeholder·extension closure의 boundedness

**준비:** 비밀이 아닌 synthetic credential shape와 고정 local provider stand-in, 지원 rootfs/spawn plan

**동작:** credential 해석 실패, placeholder 생성 재시도, timeout/close, 큰 응답/입력 경계를 시험한다.

**관측해야 할 결과:** 실제 credential은 코드/로그/환경/sandbox 파일로 새로 기록되지 않는다. placeholder 생성은 유한하게 끝나거나 명시 거절하고 socket/task lifetime이 제한된다.

**음성 대조군:** 무제한 recursive retry, provider 응답 전체 적재 또는 secret logging control이 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

가격/usage 회계를 refactor 명목으로 재도입, credential을 환경이나 snapshot에 저장, provider 별 공격 요청 구성, session notification만으로 power-loss 증명, tool hidden을 OS isolation으로 주장, engine 자동 탐색/fallback을 새로 열기, 암묵적 dependency upgrade를 금지한다.

## 6. 호환성·실패·롤백

C0/C1. engine major/schema upgrade와 비용 상한 복원은 별도 제품 결정이다. 권한·native boundary 강화를 위해 공개 의미가 바뀌면 C2/C3로 승격한다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

실제 잠긴 엔진에서 production plan의 로드·이벤트·자원수명 계약이 확인된다. relay/placeholder 결과는 bounded이며 보안 경계는 유지된다. S-02/S-03 등 검증되지 않은 보장은 OPEN/BLOCKED로 남긴다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
