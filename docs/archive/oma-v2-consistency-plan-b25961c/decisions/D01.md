# D01 — Delivery evidence와 run ownership을 분리하되 우선 v1을 유지한다

상태: **PROPOSED — WP01에서 현재 규범과 대조해 확정할 결정**. 구현이 완료됐다는 기록이 아니다.

## 문제와 선택

batch의 incarnation은 재할당되고, receipt의 incarnation은 최초 전달 시점에 고정된다. 현재 decoder는 양자의 정확한 일치를 요구한다. 재시작 뒤 둘을 임의로 맞추지 않는다. 우선 선택은 **기존 batch incarnation과 일치하는 유효 receipt의 정산을 rollover보다 먼저 수행**하는 것이다. 새 DB table/column, wire state, receipt version을 먼저 만들지 않는다. [S06](../guide/SOURCES.md#s06), [S07](../guide/SOURCES.md#s07), [S08](../guide/SOURCES.md#s08), [S71](../guide/SOURCES.md#s71).

## 의미의 분리

BatchIdentity는 actor+batch id+순서를 포함한 exact message manifest를 뜻한다. DeliveryEvidenceIdentity는 그 batch가 특정 incarnation의 특정 session boundary에서 전달됐다는 기록을 뜻한다. RunLease는 현재 요청자의 실행 권한이다. 이것들은 별개의 개념이지만 v1 byte encoding은 유지할 수 있다. 새로운 타입만으로 linear usage가 보장된다고 주장하지 않는다.

## Rollover 순서

1. broker singleton과 현재 runner invocation을 확인한다. 이전 run에 대한 pin이 있으면 기존 RunRegistry의 empty/removed 증명을 유지한다. broker 재시작 경로는 기존 startup quiescence가 선행해야 한다. 새 runner가 active라는 이유로 이전 run이 dead라고 추측하지 않는다.
2. 새 endpoint에 권한을 주기 전에 현재 durable agent incarnation과 prepared batch snapshot을 읽는다.
3. 기존 incarnation과 정확히 일치하는 receipt를 bounded read로 검증한다. receipt validator가 요구하는 actor/id/manifest/adapter/session relation을 보존한다.
4. 증거가 유효하면 broker-owned 좁은 recovery API에서 해당 배치만 complete한다. 증거 관측은 transaction 밖에서, 그 관측의 batch identity/state가 여전히 같은지 transaction 안에서 재확인한다. 이 단계는 모델·tool을 실행하지 않는다.
5. 나머지 prepared batch 중 receipt 부재가 관측된 항목만 현재 정책에 맞게 재할당한다. 증거 부재가 tool 효과 부재를 뜻하지 않으므로 기존 operation receipt 안내/멱등 key 정책을 유지한다.
6. incarnation 증가 및 남은 batch 재할당을 기존 root transaction에서 수행하고 endpoint를 publish한다. 각 경계의 실패 시 보존 대상과 다음 run에서의 재진입을 시험한다.

작업 중 runRegistry.begin가 이전 pin을 종료하는 위치와 receipt I/O의 위치를 검토한다. death proof가 이미 성립한 좁은 section을 사용하되, 실패한 opening run을 live처럼 반환하거나 다음 재시도를 영원히 막는 새 상태를 만들지 않는다. 같은 invocation의 idempotent open과 재시작 invocation을 별도 시험한다.

## 공통 evidence 판정

| 관측 | 새 전달 | 정산 | 처리 |
|---|---|---|---|
| exact verified receipt | 금지 | 허용 가능한 현재 host authority 아래 진행 | 최초 유효 receipt를 기준으로 완료 |
| receipt name 부재가 확인됨 | domain의 중복 안내 정책에 따라 검토 | 증거 없는 완료 금지 | 기존 attempt 도구 효과 부재라고 추정하지 않음 |
| 읽기 불가/일시 I/O | 금지 | 보류 | 원인·재관측 필요 표시 |
| 형식 손상/identity conflict | 금지 | 금지 | 증거 보존·명시적 repair |
| batch.completed | 금지 | exact replay만 허용 | 최초 terminal fact 보존 |

Principal에서는 `tick` 시작에 settlement 후보를 먼저 처리한다. 유효 receipt 정산은 새 model turn이 아니므로 engine busy/offline이라는 이유로 불필요하게 차단하지 않는다. 단 host endpoint의 실제 인증·등록 계약은 유지한다. 필요하다면 등록 불가 상황은 trusted broker startup recovery에서 정산하고, 임의 client에게 offline complete를 열지 않는다.

## 영수증 publication의 보장

파일 내용을 썼다는 것만으로 durable receipt를 반환하지 않는다. bounded bytes를 private temp에 쓰고 파일 fsync 후, 최종 이름을 no-replace로 게시하고 parent directory fsync를 수행한다. 기존 receipt가 있으면 identity를 검증해 재사용하고 그 반환값이 completion의 기준이다. `publishImmutableFile`은 현재 0444 mode를 적용하므로 receipt의 0600 계약을 몰래 바꾸는 직접 재사용은 금지한다. [S46](../guide/SOURCES.md#s46), [S47](../guide/SOURCES.md#s47).

## 기존 불일치 데이터

rollover가 이미 수행된 뒤 남은 옛 receipt를 자동으로 새 incarnation에 끼워 맞추지 않는다. inventory 진단은 상태·expected/observed identity를 보여주되 내용을 수정하지 않는다. provenance를 검증할 수 있는 별도의 offline repair만 고려한다. 구체적인 증거가 없다면 안전하게 blocked로 남기는 것이 정답이다. 이 계획은 불충분한 역사에서 새 사실을 복원하지 않는다.

## 보장하지 않는 것

유효 receipt가 없을 때 모든 외부 효과가 exactly-once로 실행됨, Pi notification 자체가 session 디스크 flush의 증명임, 단순 readonly 타입이 재실행을 금지함을 보장하지 않는다. S-03의 pinned engine persistence 증거는 WP27/30에서 별도로 요구한다. 기존 contract가 v1 해결을 허용하지 않으면 C3 migration을 즉석 추가하지 말고 결정 변경을 기록한다.

정산 API·관측 결과·failure ordering의 구체적인 계약은 [DELIVERY-CONTRACT](DELIVERY-CONTRACT.md)을 따른다.
