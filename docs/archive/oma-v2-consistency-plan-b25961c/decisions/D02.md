# D02 — 설정 읽기는 한 snapshot, 관리형 쓰기는 한 generation commit

상태: **PROPOSED**. 수동 operations bundle의 현재 비원자성을 기존 계약 위반으로 단정하지 않는다. 운영 문서는 이를 명시적으로 보장하지 않는다. 다만 제품의 관리형 편집에 강한 일관성을 추가하기 위해 C2 변경을 제안한다. [S64](../guide/SOURCES.md#s64)

## 기본 선택

inline config는 validate→동일 파일 durable replace를 유지한다. 수동 operations-v1 읽기를 유지하면서, 관리형 편집은 index 디렉터리 안의 immutable generation을 만들고 기존 manifest 파일을 마지막에 한 번 교체한다. manifest key는 kind/host/models/roles를 유지한다. 아래 경로는 제안된 내부 저장 배치이며 WP01에서 확정한다.

```text
bundle/config.json                             # 유일한 commit pointer; 일반 JSON 파일
bundle/.oma-config/generations/<generation>/
  host.json
  models.json
  roles/<profile>.json
  prompts/<profile>.md
```

`current` symlink를 새로 만들지 않는다. reference는 기존 loader가 허용하는 normalized relative path이며, 최상위 config path를 명시적으로 realpath 처리하는 기존 계약과 구분한다.

## Reader 계약

한 호출은 manifest bytes를 한 번 읽고 그 snapshot에서 layout과 role/host/model을 만든다. `readSettings`가 loadConfig와 configurationLayout을 독립 호출해 두 세대를 섞지 않도록 `loadConfigurationSnapshot` 계열의 좁은 결과를 공유한다. 이 이름은 제안이며 실제 owner 위치는 WP12에서 정한다.

구세대 reader가 파일을 여는 중 새 generation이 publish되어도 구세대 파일은 유지한다. 신규 managed reader는 root·generation·실제 읽은 file identity를 묶고 파일당 budget, 전체 closure budget, UTF-8·closed shape를 검증한다. 수동 파일이 동시 수정되면 silent mixture 대신 명시적 읽기 실패를 허용한다. 프로세스별 snapshot은 다를 수 있지만 한 snapshot 안에서 섞이면 안 된다.

## Writer 순서

1. host tenure와 편집 대상의 현재 config version을 확인한다. 오래된 settings snapshot으로 무조건 덮어쓰지 않는다.
2. 불변 편집 command로 전체 후보를 만든다. profile/model 존재와 quota 교차 조건을 포함해 실제 loader와 같은 순수 validator를 통과시킨다.
3. 새 generation에 host/models/roles와 참조하는 prompt bytes를 작성한다. 역할 파일의 `promptFile`은 **index root 기준**이므로 generation 내부의 새 상대 경로로 올바르게 재기록한다. role 파일 기준으로 해석하지 않는다.
4. 의미 없는 unknown fields를 새로 허용하지 않으면서 기존에 허용된 toolSurface와 prompt/extension 설정을 보존한다. 같은 role file을 여러 profile이 가리키는 수동 bundle은 migration 시 profile별 사본으로 펼치되 effective config의 동등성을 검사한다.
5. 파일 fsync→generation directory 및 새 directory chain fsync→manifest temp 파일 fsync→manifest atomic replace→manifest parent fsync 순서를 지킨다.
6. commit이 관측·영속화됐음을 확인한 뒤 성공을 알린다. rename 이후 fsync 실패는 결과 불명으로 보고, 관측 전에 구파일로 rollback하지 않는다.
7. writer는 더 이상 old role/host 파일을 제자리 수정하지 않는다. 불완전 generation은 cleanup 대상이 될 수 있으나 현재/이전 reader가 참조할 수 있는 generation은 즉시 삭제하지 않는다.

## Identity와 revision

manifest publication generation, effective HostConfig 정책 identity, external deployment digest는 서로 다르다. generation은 작성된 설정/프롬프트의 snapshot을 식별한다. extension 코드 파일을 config generation이 immutable로 만든다고 주장하지 않는다. libdir code는 deployment manifest와 spawn 직전 integrity 검사가 소유한다.

기존 persisted request/spec hash recipe를 변경하지 않는다. `integration.policyRevision`은 실제 정책 변경에 따라 기존 규범이 정한 대로 갱신한다. full snapshot identity와 그 필드를 같은 것으로 취급하지 않는다. generation ID 산출은 새 내부 recipe로 문서화하되 자기 자신의 경로 문자열을 hash에 포함해 순환하지 않도록 logical relative names와 bytes를 사용한다.

## 보관·정리

구세대를 무제한 보관하는 것도 실패다. 첫 구현에서는 generation 수/전체 bytes의 보수적 관리 한도를 결정하고, 한도를 넘으면 편집을 명시적으로 거절한다. 안전한 GC는 quiescent maintenance에서 active/last-known-good/reference closure를 제외하고 수행한다. 어떤 live reader도 쓰지 않음을 증명하지 않고 시간 경과만으로 삭제하지 않는다. “무제한 보관으로 안전”도 “오래된 파일 모두 삭제로 간단”도 금지한다.

## Compatibility

수동 편집과 managed generation 편집을 명확히 표시한다. 기존 바이너리의 writer는 generation을 제자리 수정할 수 있으므로 managed mode 승격 후 사용하지 않는다. 필요 시 explicit export로 기존 flat bundle을 생성한다. 자동 flattening/원본 덮어쓰기 금지. C3 schema 변경 없이 해결하되 운영 계약은 반드시 문서화한다.

## 보강: version 검사와 commit 사이의 직렬화

host tenure 보유와 편집 두 개의 non-interleaving은 같은 보장이 아니다. 관리형 config owner는 expected-version read/compare부터 pointer publication까지 하나의 critical section으로 직렬화한다. in-flight 편집은 명시적으로 bounded하게 하고 마지막 순간 비교만 하고 await하는 check-then-use 구현을 CAS라고 부르지 않는다. 비협조적인 external same-UID writer까지 완전하게 봉쇄한다는 보장은 하지 않으며 수동 동시 편집 금지 조건을 유지한다. 자세한 결과·입출력 계약은 [CONFIG-CONTRACT](CONFIG-CONTRACT.md)을 따른다.
