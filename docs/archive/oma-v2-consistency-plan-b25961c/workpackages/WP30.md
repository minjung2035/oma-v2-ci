## 1. 이 작업이 필요한 이유와 판정의 강도

여러 helper 시험이 통과해도 모듈 간 의미가 일치한다는 뜻은 아니다. 이 작업은 앞선 수정들이 연결된 production path에서 동일 불변식을 지키는지 검증한다. 새로운 결함이 나오면 해당 owner WP를 재개하고 통합 시험만 우회하지 않는다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP30.01 — 독립 모형

expected behavior는 승인된 ADR/결정표에서 작성하고 production branch/helper를 복사하지 않는다. impossible combination과 reachable-but-unknown 상태를 구분한다. 전체 조합이 너무 크면 동등 클래스와 제외 이유를 명시한다.

### WP30.02 — crash point mapping

verification/FAULT-MATRIX의 준비·가시화·파일 flush·parent flush·ledger commit·응답 경계마다 실제 seam을 연결한다. injected exception은 cleanup을 실행하고 process crash는 실행하지 않는 차이를 시험한다. 중단한 사실이 실제 경계였는지 parent가 관측한다.

### WP30.03 — safety와 liveness 분리

증거 보존과 중복 효과 방지뿐 아니라 정상 조건 회복 후 정산 진행도 검사한다. 영구적인 unknown을 근거 없이 success로 전환하지 않으며 불명/손상 상태는 repair 경로와 함께 남긴다. timeout을 모든 문제의 해결책으로 사용하지 않는다.

### WP30.04 — semantic mutation 증명

F/N 각 수정의 원인 분기를 disposable worktree에서 최소로 되돌려 새 회귀 시험이 실패함을 확인한다. arbitrary exploit 생성이나 외부 target probing은 하지 않는다. 테스트를 깨기 위한 unrelated syntax error는 유효한 mutation 증거가 아니다.

### WP30.05 — 환경별 qualification

node/git-fs/engine/pty/kernel/crash/powercut/provider 원시 결과를 분리한다. 권한/환경이 없으면 정확한 항목을 BLOCKED로 남긴다. release를 위해 필요한 lane은 code-complete와 별개로 반드시 통과해야 한다.

## 4. 회귀 시험 — production 경로를 사용한다

### V30A — 독립 상태 모형과 composed runtime

**준비:** delivery/config/preaccept/operation의 독립 상태 결정표와 실제 Store/FS/engine adapters

**동작:** 도달 가능한 state/event 조합을 생성해 interruption/restart/중복응답/늦은응답을 교차 실행한다.

**관측해야 할 결과:** 고정된 사실은 퇴행하지 않고 old auth는 new effect를 승인하지 않는다. 유한 장애 후 지원 조건이 회복되면 정책상 복구 가능한 작업은 진행한다. 모든 거절도 안전한 실패 이유를 남긴다.

**음성 대조군:** 이 감사의 수정 분기를 되돌린 최소 semantic mutant별로 적어도 하나의 독립 oracle가 실패한다.

**lane / 현재 실행 상태:** `property` / `NOT_RUN`.
### V30B — 실제 crash와 release 환경

**준비:** 소유자가 승인한 disposable systemd user와 fresh source-bound build, raw 로그 저장

**동작:** 지원 topology별 process kill/restart, 파일 게시/DB commit 경계, 실제 pty/engine를 검증한다. powercut은 별도 승인된 VM에서만 한다.

**관측해야 할 결과:** 프로세스 crash, kernel lifecycle, VM power-loss, real-provider 시험의 결과를 분리한다. skips/NOT_RUN은 PASS가 아니고 미지원 경로는 기존 gate를 유지한다.

**음성 대조군:** mock unit 성공이나 SIGKILL만으로 power-loss 항목을 PASS로 채운 증거를 거절한다.

**lane / 현재 실행 상태:** `kernel` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

모형 expected를 production 함수로 생성, 모든 경우 fail-closed이므로 liveness 생략, skip을 성공 합계에 포함, 테스트 전용 정상화로 broken legacy data를 자동 수리, 실제 사용자 프로세스/상태에 kill/fault 주입을 금지한다.

## 6. 호환성·실패·롤백

C0 verification. 이 작업은 VM/계정/서비스를 자동 생성하거나 GitHub에 write하지 않는다. 실제 provider 비용·disposable 환경·powercut은 운영자 승인 범위에서만 수행한다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

각 수정은 실제 production 결합 회귀와 최소 semantic mutant에 연결된다. source-bound raw evidence와 남은 gates가 있고 safety/liveness를 각각 판정한다. 필요한 환경 없는 항목은 미완료로 남는다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
