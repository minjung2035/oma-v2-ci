## 1. 이 작업이 필요한 이유와 판정의 강도

configurationLayout owner가 생겼지만 readSettings는 config와 layout을 독립해서 읽는다. generation commit을 도입해도 reader가 두 번 pointer를 읽으면 다른 세대를 섞을 수 있다. layout의 단일 정의와 snapshot의 단일 읽기는 다른 요구다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP12.01 — 읽기 결과 설계

단일 호출이 validated config, roles, authored layout, source observation identity를 반환하게 한다. 각 field의 identity는 실제 읽은 bytes/manifest에 묶는다. layout-only 진단과 full validated snapshot을 타입·함수명에서 구분한다.

### WP12.02 — manifest 한 번 해석

top-level path의 기존 symlink 허용 계약을 유지하면서 resolved index를 한 번 읽고 그 byte snapshot에서 모든 상대 참조를 확정한다. role/models/host의 independent parser를 screen에서 제거한다.

### WP12.03 — asset reader 보존

파일당 1MiB, role64, extension16 등 기존 제한을 유지하고 복수 파일 합계·항목 수를 관리한다. index-root prompt semantics를 유지한다. stable FD/후검증을 통해 읽는 동안 변경된 파일을 조용히 사용하지 않는다.

### WP12.04 — caller 이관

settings/session/runner가 snapshot을 공유하거나 각 activation에 완전한 새 snapshot 하나를 읽도록 한다. 화면 한 번 그리는 동안 load/layout/extensions가 서로 다른 generation을 선택하지 않게 한다.

### WP12.05 — manual source 제한

수동 편집 bundle은 concurrent write가 없다는 기존 운영 조건을 표시한다. 감지한 drift는 명시적으로 읽기 실패로 처리한다. managed mode와 달리 arbitrary same-UID writer가 수정하지 못한다는 보장을 추가하지 않는다.

## 4. 회귀 시험 — production 경로를 사용한다

### V12A — 한 read는 하나의 manifest snapshot

**준비:** 구세대/신세대 host/models/roles/prompts가 완전하게 다른 managed bundle

**동작:** manifest read 이후 pointer를 교체하면서 settings와 extensions를 읽는다.

**관측해야 할 결과:** 한 반환 snapshot은 오직 한 세대에서 온다. config와 layout을 별도로 다시 읽어 혼합하지 않는다.

**음성 대조군:** loadConfig 후 configurationLayout을 재호출하는 control이 mixed-version fixture에서 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V12B — 정확한 prompt root와 bounded source closure

**준비:** nested role paths·shared prompt·index의 명시 symlink·파일 크기 한도 fixture

**동작:** 전체 source snapshot을 읽고 logical reference를 해석한다.

**관측해야 할 결과:** promptFile은 index root 기준이며 existing normalization/regular-file 제한을 유지한다. 전체 closure budget을 넘으면 명시적으로 거절한다.

**음성 대조군:** role dirname 기준으로 prompt를 해석하거나 unlimited read로 바꾸면 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

derived layout을 오래 보관해 write authority로 사용, root containment 검사 생략, source byte identity 없이 generation이라고 이름만 붙임, prompt 상대 경로 기준 변경, silent inline fallback을 금지한다.

## 6. 호환성·실패·롤백

C0/C2 reader 준비 단계. 아직 writer generation 전환을 수행하지 않는다. old inline/operations fixture를 모두 읽을 수 있어야 WP13 producer 전환이 가능하다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

모든 product config consumer가 하나의 snapshot을 받거나 독립된 완전한 activation snapshot을 받는다. 한 반환값에서 mixed-generation이 생기지 않음이 실제 파일 교체 시험으로 확인된다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.

추가 읽기: [CONFIG-CONTRACT](../decisions/CONFIG-CONTRACT.md). partial authored source와 runnable validated snapshot을 구별한다.
