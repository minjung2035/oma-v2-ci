| 항목 | 실행 계약 |
|---|---|
| 시작 상태 | NOT_STARTED. 테스트와 제품 검증은 NOT_RUN |
| 기준 source | `minjung2035/oma-v2` / `refactor/safety-preserving-architecture` / `b25961cc46532f5e30ff60cc381fed51c59d13ab` |
| 선행 작업 | 없음 |

## 1. 이 작업이 필요한 이유와 판정의 강도

이 계획의 source-level finding이 현재 checkout에서도 성립하는지 먼저 확인해야 한다. GitHub HEAD는 고정됐지만 구현 AI의 working tree는 달라질 수 있다. 과거 test count와 문서의 구조 완료 선언을 fresh evidence로 사용하지 않는다. 이 작업은 코드 수정보다 검증 가능한 출발점을 만드는 작업이다.

## 2. 시작 전에 읽을 source와 변경 경계

- [S01](../guide/SOURCES.md#s01) — `MAINTENANCE.md`: 1–440행: Fact/Relation/Phase, 규범 우선순위, 복구·검증 규율
- [S33](../guide/SOURCES.md#s33) — `scripts/source-digest.mjs`: 전체: verification input closure와 self field normalization
- [S34](../guide/SOURCES.md#s34) — `scripts/verification-lanes.mjs`: 1–240행: 로컬 제외 시험/fast/durable/kernel/crash/property/stress 일부
- [S35](../guide/SOURCES.md#s35) — `scripts/build.mjs`: 전체: 고정 dist layout와 package 검사
- [S36](../guide/SOURCES.md#s36) — `package.json`: script와 의존성 버전 선언; 이전 동일 SHA 검토

아래는 **검토·수정 가능한 후보 범위**다. 모두를 바꾸라는 뜻이 아니다. 실제 호출 관계를 확인한 후 필요한 최소 경로만 수정한다. 여기에 없는 production owner를 바꿔야 하면 구현 전에 범위·선행 작업·회귀 시험을 갱신한다.

- `package.json`

- `production-files.txt`
- `scripts/source-digest.mjs`
- `scripts/verification-lanes.mjs`
- `implementation/source-owners.json`

읽을 작업 문서는 이 파일, [AI 실행 규율](../guide/AI-EXECUTION.md), [불변식](../guide/PRINCIPLES.md), 위 결정 문서다. 완료한 선행 작업의 handoff를 먼저 받아 현재 HEAD와 변화를 확인한다. 서로 다른 작업의 오래된 source 사본을 합치지 않는다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP00.01 — 환경·변경 상태 기록

`git rev-parse HEAD`, `git status --short`, 현재 branch, Node/npm/Git/SQLite 버전과 OS·filesystem·systemd user manager·bwrap 여부를 기록한다. 사용자가 만든 dirty 변경은 보존한다. private repository 접근이나 package install 실패는 실제 오류로 보고한다.

### WP00.02 — inventory와 ownership map 대조

고정 production-files와 `git ls-files` 및 실제 import closure를 비교한다. 이 계획의 REVIEW-COVERAGE에 없는 새 파일, production manifest에 빠진 runtime 파일, test/script/contract 파일을 별도로 배정한다. 모든 production 파일에 주 검토 WP를 하나 지정한다. 이 단계는 읽음/정상 판정이 아니라 누락 방지다.

### WP00.03 — baseline 실행

먼저 커밋된 inventory 상태를 검사해 stale 여부를 보존한다. 그다음 package scripts의 현재 정의를 읽고 의존성 설치, typecheck/build/check:package/check:architecture/local tests를 실행한다. generator로 잘못된 baseline을 덮은 후 원래도 맞았다고 기록하지 않는다.

### WP00.04 — finding 재분류

ASSESSMENT의 F/N/H/Q를 실제 함수와 호출 경로에서 확인한다. already-fixed이면 해당 diff와 회귀 시험을 링크하고 중복 수정을 생략한다. 실행 반례가 없는 정적 의심은 verified bug와 분리한다.

### WP00.05 — evidence directory 확정

evidence는 repository 밖의 새 디렉터리에 저장하고 commit/input digest·명령·exit-code·raw log·환경을 결박한다. 어떤 명령을 실행하지 못했는지 함께 기록한다. evidence 자체를 verification input에 무한히 포함해 self-reference를 만들지 않는다.

## 4. 회귀 시험 — production 경로를 사용한다

### V00A — source와 evidence 결박

**준비:** 별도 worktree와 저장소의 source-digest module; 실제 Git HEAD/dirty diff

**동작:** 측정 전후 digest를 기록하고 의도적으로 verification input 한 파일을 변경한다.

**관측해야 할 결과:** 변경된 input은 digest와 관련 gate의 실패로 드러나고 과거 결과를 현재 PASS로 재사용하지 않는다.

**음성 대조군:** 검증 대상 file list에서 해당 파일을 제외한 임시 negative control이 검출되지 않으면 oracle 자체를 실패시킨다.

**lane / 현재 실행 상태:** `fast` / `NOT_RUN`.
### V00B — 미지원 환경은 PASS가 아니다

**준비:** 실제 Node/Git/SQLite/bwrap/systemd availability table

**동작:** 지원되는 lane과 지원되지 않는 lane을 구별해 dry qualification한다.

**관측해야 할 결과:** unavailable lane은 BLOCKED/NOT_RUN과 이유가 있으며 local suite 결과와 별도다.

**음성 대조군:** skip된 test가 포함된 summary를 성공으로 받아들이는 변경을 검출한다.

**lane / 현재 실행 상태:** `fast` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

working tree 강제 reset, 과거 성공 로그 복사, baseline generator 차이를 숨김, npm ci 실패를 무시한 typecheck 결과 채택, systemd 없는 모형 PASS를 kernel qualification으로 표기하는 것을 금지한다.

## 6. 호환성·실패·롤백

C0의 검증·문서 작업이다. runtime state를 만들거나 수정하지 않는다. package install이 필요한 경우 repository-local dependency 외의 운영 환경 변경은 별도 확인한다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

현재 모든 tracked production 파일이 WP에 배정돼 있고 baseline 결과가 source에 결박된다. 각 finding의 현재 상태가 기록되면 WP01/02로 넘긴다. 로컬 baseline failure는 사유와 영향 task를 명시한 채 보존하며 코드 수정으로 baseline을 조작하지 않는다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
