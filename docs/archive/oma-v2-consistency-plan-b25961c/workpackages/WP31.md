## 1. 이 작업이 필요한 이유와 판정의 강도

소스 구조가 일관돼도 배포본이 다른 engine/config/schema를 읽으면 같은 시스템이 아니다. read-config generation과 launch locator를 실제 install artifact에서 확인하고, 개발 source에서만 되는 실행을 release 성공으로 취급하지 않는다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP31.01 — 현재 지원표 고정

package/compiler/workflow/operating docs에서 실제 Node·OS·native modules·systemd·rootfs·engine 범위를 확인한다. 버전은 최신이라는 이유로 바꾸지 않는다. 명시하지 않은 지원 범위는 추측 대신 실제 검증 조건으로 남긴다.

### WP31.02 — fresh build closure

기존 build script의 dist 정리·tsc·check-package 순서를 유지한다. source/test 혼입·symlink outdir·runtime assets의 상대 위치·bundled engine executable을 확인한다. build output을 손으로 고쳐 통과시키지 않는다.

### WP31.03 — artifact-only smoke

실제 배포 방식으로 만든 산출물만 임시 install prefix에 두고 실행한다. package manifest에 없는 bin/install command를 있다고 가정하지 않는다. 현재 entry 노출이 불완전하면 packaging 결함으로 기록해 해당 파일에서 닫는다.

### WP31.04 — identity·config 전달

고정 node/libdir/deployment digest와 custom config locator가 모든 실제 child/unit에 이어지는지 확인한다. config generation이 바뀌어도 frozen accepted data를 현재 generation으로 재해석하지 않는다.

### WP31.05 — dependencies와 증거

lockfile 설치 결과와 native 모듈·엔진 버전을 기록한다. dependency upgrade가 필요하면 별도 review/risk/test 항목으로 분리한다. deployment manifest와 source evidence digest를 서로 대체하지 않는다.

## 4. 회귀 시험 — production 경로를 사용한다

### V31A — 실제 배포 산출물의 closure

**준비:** clean checkout의 locked dependencies/build와 실제 지원 install artifact, 별도 임시 prefix

**동작:** artifact만으로 entry/schema/systemd/engine/extension resolution과 custom config path를 실행한다.

**관측해야 할 결과:** source tree의 우연한 파일이나 PATH의 외부 Pi에 의존하지 않고 선언된 bundle을 사용한다. 없어야 할 test source/secret은 closure에 없다.

**음성 대조군:** 원본 repo 위치가 없으면 시작 못 하거나 다른 설치본 schema/engine으로 fallback하는 control이 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V31B — runtime 지원 범위와 manifest 동기화

**준비:** 정확한 지원 Node/OS/profile matrix, dependency lock·deployment digest

**동작:** 깨끗한 build를 재측정하고 missing/mismatched assets를 확인한다.

**관측해야 할 결과:** 출처·버전·asset mismatch는 명시 실패한다. read/write compatibility와 actual engine pin을 분리해 기록한다.

**음성 대조군:** 현재 배포본이 아닌 stale dist나 임의 dependency update를 같은 결과로 기록하면 실패한다.

**lane / 현재 실행 상태:** `fast` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

PATH Pi fallback, 다른 checkout의 schema 사용, stale dist 수동 patch, npm install로 lock 변화를 숨김, package에 없는 실행 명령을 문서에 단정, 자동 dependency upgrade와 state migration의 혼합을 금지한다.

## 6. 호환성·실패·롤백

C0/C1, install surface/지원 범위를 바꾸면 C2. package/engine version update는 자동 포함이 아니다. 구버전 writer를 managed generations에 연결하지 않는 배포 절차를 제공한다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

clean build와 artifact-only smoke가 선언된 설치 방식에서 통과한다. configuration writer의 backward incompatibility까지 지원표에 있으며 출처를 확인할 수 있는 manifest와 raw 결과가 남는다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
