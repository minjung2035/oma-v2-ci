## 1. 이 작업이 필요한 이유와 판정의 강도

Git에는 이미 normal/recovery 분리, expected-old CAS, immutable published ref, current-authority 재검사가 있다. 이 작업은 이를 generic workflow로 합치지 않고 전체 Git 경로가 같은 Fact/Relation/Phase를 쓰는지 확인한다. H02는 no-op 의미의 계약 결정이며 현재 nonempty check gate를 우회하는 확정 취약점이 아니다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP24.01 — 현재 effect 표 작성

각 mutation에서 intent commit, object import, ref CAS, snapshot, mail, terminal commit의 순서와 linearization point를 기록한다. canonical ref의 관측과 해당 operation이 효과를 냈다는 증거를 혼동하지 않는다. source를 읽지 않은 하위 파일도 이 단계에서 직접 검토한다.

### WP24.02 — 정상·복구 결정표 유지

같은 observation primitive와 validation recipe를 재사용하되 execute와 reconcile의 결정 순서는 따로 둔다. actual effect가 이미 적용됐으면 검증된 증거를 정산한다. effect가 필요하면 current state/policy/authority와 writer slot을 확인한다.

### WP24.03 — no-op 명세 적용

D06의 승인된 no-op 정의를 normal/recovery 양쪽에 반영한다. base=candidate는 ref equality만으로 실행 이력을 증명하지 않는다. 필요한 현재 policy/stop 조건을 다시 확인하되 실제 과거 CAS의 완료 증명까지 무효화하지 않는다.

### WP24.04 — 공통 오류 해석

corrupt/absent/unavailable/third value를 보존하고 phase/effect knowledge를 error owner에 넘긴다. failed로 확정할 근거가 없는 작업은 unknown/pending을 유지한다. 새로운 observable state를 무조건 DB enum으로 만들지 않는다.

### WP24.05 — 형식·경로·비용 회귀

actual object format, full OID, literal protected paths, bundle prerequisites와 고정 Git 환경을 시험한다. Git checks는 kernel workspace profile이 검증되기 전에는 계속 거절한다. IO bound 개선이 출력을 조용히 잘라 올바른 complete observation처럼 만들지 않게 한다.

## 4. 회귀 시험 — production 경로를 사용한다

### V24A — Git CAS 실패와 recovery의 역사적 사실

**준비:** 실제 SHA-1/SHA-256 저장소, frozen accepted integrate/context/submit intent, candidate/base/third ref 세 상태

**동작:** CAS 전후 실패를 주고 recovery를 반복한다.

**관측해야 할 결과:** third ref를 덮어쓰지 않고 이미 확인된 publication은 보존한다. 새 효과를 낼 때 현재 권한·정책을 검사하며 unsupported check profile을 실행하지 않는다.

**음성 대조군:** current HEAD로 candidate를 재생성하거나 CAS 실패를 success로 치환하는 control이 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V24B — no-op integration의 계약 분리

**준비:** base=candidate인 수락된 intent와 이후 stop/policy 변경, 실제 base!=candidate인 이미 적용된 intent

**동작:** D06 결정대로 normal/recovery 양쪽 결과를 비교한다.

**관측해야 할 결과:** no-op의 승인 의미를 동일하게 적용한다. 실제 적용된 과거 효과의 정산을 현재 정책만으로 지우거나 실패로 바꾸지 않는다.

**음성 대조군:** 모든 candidate==main을 무조건 같은 성공으로 처리하거나 historical effect를 새 auth로 무효화하는 control이 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

모든 recovery를 original request replay로 통합, third OID 덮어쓰기, unknown을 absent로 처리, check 목록을 빈 배열로 바꿔 gate 통과, pending intent를 현재 config로 재작성, no-op를 빌미로 권한 검사를 모두 제거하는 것을 금지한다.

## 6. 호환성·실패·롤백

C0/C1, no-op 승인 의미를 변경하는 부분은 C2/D06. accepted plan/result byte recipe 및 canonical ref namespace는 유지한다. 과거 intent를 되돌리거나 새 ref로 보정하지 않는다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

Git family별 결정표와 actual refs/objects/mail/ledger oracle가 연결된다. H02는 채택된 계약과 그 회귀 시험으로 닫거나 명시적 미해결로 남는다. OPEN candidate execution은 확인 없이 닫지 않는다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
