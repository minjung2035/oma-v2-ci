## 1. 이 작업이 필요한 이유와 판정의 강도

영수증 파일의 writer를 공유하는 것만으로 재실행 정책이 공유되지 않는다. receipt 관측 결과와 settlement를 수행할 권한을 하나의 좁은 계약으로 만들되, 현재 public complete의 strict fencing을 유지한다. 이는 generic trusted boolean을 도입하는 작업이 아니다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP06.01 — 증거 관측 union

기존 readDeliveryReceipt/observeDeliveryReceipt의 검증을 재사용해 verified-present/observed-absent/unavailable/conflict를 보존한다. 원인과 expected/observed identity를 diagnostics에 넣되 세션 본문이나 credential은 노출하지 않는다.

### WP06.02 — 검증의 생성 owner

CheckedReceipt와 expected BatchSnapshot은 validator만 생성하도록 module 경계를 좁힌다. TS cast만으로 권한이 생기는 구조를 피하고 transaction에서 batch id/actor/incarnation/manifest/state의 불변 관계를 다시 확인한다. header-only session fixture를 완전한 persisted boundary 증거라고 부르지 않는다.

### WP06.03 — live와 recovery API 분리

live complete는 기존 AuthContext와 현재 incarnation을 그대로 요구한다. broker-owned recovery는 startup/run-open coordinator만 사용하는 별도 진입점을 둔다. API는 immutable receipt를 정산할 수 있을 뿐 새 batch 생성/engine 실행/권한 임의 부여를 제공하지 않는다.

### WP06.04 — 수락/완료 replay 정책

completed batch에 대한 exact replay는 최초 fact를 유지한다. current actor가 retired/stopped인 경우 과거 효과 정산과 새 효과 금지를 D01에 맞게 분리한다. 모든 historical complete를 광범위하게 허용하지 않는다.

### WP06.05 — caller 이관 준비

Resident/Principal이 공통 observer 결과를 통해 다음 action을 선택하도록 adapter 타입을 준비한다. 기존 public wire와 DB enums는 바꾸지 않는다. 잘못된 형식이 null fallback으로 빠지는 독립 구현을 제거한다.

## 4. 회귀 시험 — production 경로를 사용한다

### V06A — receipt 관측 네 상태 분리

**준비:** 동일 batch의 valid/absent/unreadable/identity-conflicting file; 완전한 세션 fixture

**동작:** 공통 receipt observer를 통해 normal/recovery 소비자의 결정을 비교한다.

**관측해야 할 결과:** valid만 settlement에 사용되고 absent/unavailable/corrupt가 서로 다른 결과다. IO failure는 새 전달의 근거가 아니다.

**음성 대조군:** catch-all→null 또는 incarnation inequality를 느슨하게 하는 control이 검출된다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V06B — historical settlement가 stale caller 권한을 되살리지 않음

**준비:** 과거 정확한 receipt, 현재 run lease, stale runner connection, broker-owned recovery context

**동작:** live complete와 trusted recovery를 각각 호출한다.

**관측해야 할 결과:** stale live complete는 계속 거절된다. recovery는 지정된 immutable batch/receipt만 정산하고 model/tool을 실행하지 않는다.

**음성 대조군:** recovery flag 하나로 public authentication을 우회하는 구현은 negative control에서 실패한다.

**lane / 현재 실행 상태:** `kernel` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

`trusted: true` 매개변수로 authority를 생략하거나 임의 caller가 CheckedReceipt를 생성하는 exported constructor, receipt.incarnation<=current만 검사, stale live complete 허용, 세션 전체를 무제한 읽어 증거를 보강하는 방식을 금지한다.

## 6. 호환성·실패·롤백

C0/C1. wire/DB v1은 유지한다. 기존 relational decoder의 integrity 검사를 우회하지 않는다. 과거 mismatched receipt를 처리하려면 진단 후 explicit repair 계획을 별도로 적용한다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

표의 네 상태가 모든 소비자에게 같은 의미로 보인다. live completion과 historical settlement의 허용 경계가 문서·타입·runtime test에 일치하고 두 경로 모두 stage/identity 오류를 거절한다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.

추가 읽기: [DELIVERY-CONTRACT](../decisions/DELIVERY-CONTRACT.md). 기존 identity 비교의 약화 없이 그 계약을 충족해야 한다.
