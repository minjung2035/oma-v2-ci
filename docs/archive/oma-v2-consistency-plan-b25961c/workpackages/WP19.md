## 1. 이 작업이 필요한 이유와 판정의 강도

bootstrap의 Promise.all은 일부 branch가 artifact를 만든 뒤 다른 branch가 실패할 수 있고, create의 freeze 이후 policy refresh도 수락 전 실패다. linked create는 accepted row가 존재해도 새 initialMessage를 소유하지 않는다. 이 세 경우를 같은 ownership 규칙으로 처리한다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP19.01 — bootstrap 준비 방식

원자적 seed transaction은 유지한다. 준비 작업은 순차 또는 명시적으로 제한된 동시성으로 수행하고 첫 실패 이후에도 시작한 branch의 정산을 끝낸 뒤 scope를 닫는다. 필요 없는 무제한 Promise.all을 유지하지 않는다.

### WP19.02 — artifact 등록과 policy refresh

freeze 직후 scope 등록을 완료하고 모든 refresh/resolve/final auth/TX를 그 범위에 둔다. failed refresh에서 이전 cached policy를 재사용하지 않는 기존 createChildSpecResolver 동작을 유지한다.

### WP19.03 — physical vs linked

same-name/same-spec winner 결정은 transaction이 소유한다. linked plan의 initialMessage=null에 따라 새 artifact가 실제로 accepted plan에 참조되는지 판정한다. receipt 재사용이 새 quota/workspace 소비를 만들지 않게 한다.

### WP19.04 — workspace/ready/activation

workspace 준비, unit 설치, ready commit, initial mail materialization, activation을 서로 다른 phase로 유지한다. scope를 ready까지 무조건 연장해 accepted artifact를 삭제 가능한 자원으로 남기지 않는다.

### WP19.05 — 반복·동시 호출

같은 operation의 finish 공유와 다른 operation의 bounded refusal를 유지하고 queued task를 무제한 쌓지 않는다. 종료 도중 준비 task가 뒤늦게 effect를 발행하는지 확인한다.

## 4. 회귀 시험 — production 경로를 사용한다

### V19A — bootstrap 일부 준비 실패

**준비:** 여러 initialResidents의 정상 config와 initial message freeze 중 한 branch 실패

**동작:** bootstrap을 실행하고 모든 asynchronous preparation이 끝난 뒤 ledger/files를 관측한다.

**관측해야 할 결과:** registry 전체 acceptance는 원자적이며 미수락 자원의 정리가 빠지지 않는다. 실패 뒤에도 실행 중인 branch가 늦게 파일을 남기는 orphan 작업이 없다.

**음성 대조군:** Promise.all first rejection에서 즉시 반환하는 control을 검출한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V19B — create 정책 갱신 실패와 same-name race

**준비:** 동일 이름/동일 spec의 concurrent create와 freeze 이후 policy refresh 실패

**동작:** 각 create를 실제 Store transaction까지 실행한다.

**관측해야 할 결과:** 물리 winner는 하나, linked 요청은 workspace/mail/quota를 중복 소비하지 않는다. refresh throw에서 initial artifact가 정확히 정리/보존된다.

**음성 대조군:** refresh를 정리 scope 밖에 두거나 linked plan에 initial artifact를 잘못 retain하면 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

bootstrap 실패 때 registry 일부를 남김, 준비 branch를 버리고 반환, 같은 이름의 workspace를 실패 cleanup에서 삭제, linked request가 물리 create를 다시 함, policy read를 DB transaction에 넣는 것을 금지한다.

## 6. 호환성·실패·롤백

C1. seed 계약·logical agent name 재사용 정책·quota 의미를 바꾸지 않는다. 이전 already-created registry를 새 config로 재작성하지 않는다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

bootstrap/normal/linked create 각각이 정확한 artifact disposition을 사용한다. same-spec winner 하나와 atomic seed set이 production Store/Mail/Workspace 결합 시험에서 유지된다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
