## 1. 이 작업이 필요한 이유와 판정의 강도

F01은 receipt 검증을 느슨하게 하는 것으로 고칠 수 없다. 기존 batch의 역사적 evidence를 먼저 해석하지 않고 incarnation을 바꾸는 순서가 문제다. active broker의 runner 재시작과 broker 자체 재시작을 모두 다뤄야 한다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP07.01 — rollover boundary 찾기

RunRegistry.begin의 이전 pinned cgroup empty/removed 검사와 startup quiescence를 확인한다. 새로운 runner invocation이 살아 있는 상태에서 같은 unit 이름의 confirmDead를 과거 실행 증명으로 오용하지 않는다. old pin lifetime을 조기에 닫지 않는다.

### WP07.02 — prepared receipt 정산 삽입

기존 durable incarnation을 변경하기 전에 WP06의 verified receipt 정산을 호출한다. 원래 batch identity로만 검증하고 현재 runner에게 아직 endpoint 권한을 주지 않는다. bounded read는 transaction 밖, final batch relation/complete는 동기 transaction 안에 둔다.

### WP07.03 — 남은 batch만 재할당

receipt가 없는 항목에 대해 기존 중복 안내 정책과 operation receipt 안내를 보존한다. corrupt/unavailable을 evidence 없음으로 취급하지 않는다. completed batch는 절대로 재할당하지 않는다.

### WP07.04 — 실패한 opening 복구

settlement나 incarnation transaction, listener bind 실패 후 run record가 어떤 phase에 남는지 고정한다. 같은 invocation의 replay와 새 invocation 시작을 구분한다. 실패 후 forever-busy가 되는 새 in-memory record를 만들지 않고, 필요한 경우 명시적으로 해당 invocation 종료/재시작을 요구한다.

### WP07.05 — startup와 일반 open의 대칭 검사

broker startup에서 quiesce→역사적 정산→복구→activation 순서를 검증한다. 일반 open에서도 동일 receipt 의미를 사용한다. 두 개의 독립 incarnation recovery 알고리즘을 남기지 않는다.

## 4. 회귀 시험 — production 경로를 사용한다

### V07A — receipt 저장 직후 재시작

**준비:** 실제 Store/Mail/Runner와 prepared batch, exact receipt, 완료되지 않은 ledger

**동작:** receipt가 durable한 직후 process를 종료하고 새 invocation으로 open한다.

**관측해야 할 결과:** rollover 전에 batch가 완료되고 엔진 재전달은 0회다. 후속 pending 배치가 진행하며 old receipt bytes는 바뀌지 않는다.

**음성 대조군:** 기존의 무조건 reassign-before-settle를 복원하면 회귀 시험이 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V07B — rollover의 모든 경계와 legacy conflict

**준비:** old run pin·new opening run, 증거 부재 batch와 legacy mismatched receipt

**동작:** death proof/receipt read/settlement commit/incarnation commit/endpoint publish 앞뒤에 실패를 주입한다.

**관측해야 할 결과:** duplicate live lease가 생기지 않고 ambiguous authority로 effect를 하지 않는다. legacy mismatch는 격리·진단되고 삭제되지 않는다.

**음성 대조군:** 새 runner가 active라는 사실만으로 old cgroup death를 가정한 control을 검출한다.

**lane / 현재 실행 상태:** `kernel` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

old receipt 삭제, receipt incarnation 재작성, batch ID 바꾸기, live complete의 stale check 해제, 과거 peer를 가짜 AuthContext로 만들어 public API 호출, listener publish를 DB보다 먼저 성공 처리하는 것을 금지한다.

## 6. 호환성·실패·롤백

C1이며 old batch state를 바꾸는 실제 recovery다. 운영 데이터에는 검증된 build로만 적용한다. 이미 과거 코드에서 만든 mismatch는 별도 진단/repair 상태로 남긴다. rollback이 완료 사실을 되돌려서는 안 된다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

receipt 기록 후 언제 죽어도 validated 과거 증거로 완료할 수 있는 경로가 있고, 증거가 없거나 불명일 때의 처리도 명시적이다. 실제 user-systemd invocation 재시작에서 후속 배치가 진행해야 최종 완료다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
