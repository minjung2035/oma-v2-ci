## 1. 이 작업이 필요한 이유와 판정의 강도

F12는 측정 없이 전부 async로 바꾸는 작업이 아니다. 현재 diagnostic tree scan과 per-agent synchronous observation의 비용을 측정하고 correctness-critical final check와 분리한다. 조회 projection 최적화도 relational validation을 우회하지 않아야 한다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP23.01 — 기준 부하 측정

파일/agent/operation 수별 RPC latency와 event-loop delay·FD·memory를 기록한다. 기본/상한 profile의 목표를 측정 결과에 근거해 명시한다. 30*N 이론 값을 실제 측정치로 사용하지 않는다.

### WP23.02 — diagnostic single-flight

status/scan을 async single-flight로 만들고 bounded batch/cooperative yield/timeout을 둔다. refresh 중 새 요청은 무한 queue로 쌓지 않는다. 실패한 refresh는 마지막 값의 시각/오류와 함께 unknown/stale로 표시한다.

### WP23.03 — read projection

pending count/status snapshot에 필요한 SELECT projection을 좁히되 identity/full-row 검증이 필요한 mutation/recovery 경로와 구분한다. 캐시된 decoded row를 authoritative current row로 재사용하지 않는다. 필요하면 read-only snapshot 하나 안에서 집합 관계를 검증한다.

### WP23.04 — authority 관측 분리

peer auth, current incarnation, final CAS eligibility, confirmDead는 cached diagnostic으로 대체하지 않는다. async 결과 이후 actual effect 직전 재검증과 lock/pin 수명을 WP25와 맞춘다.

### WP23.05 — 관측 실패 UX

stale/foreign/corrupt/missing view를 같은 0/empty로 보여주지 않는다. status write 실패가 Store terminal fact를 되돌리지 않고, read 요청이 새 status write 성공을 전제하지 않게 한다.

## 4. 회귀 시험 — production 경로를 사용한다

### V23A — 느린 관측 중 broker responsiveness

**준비:** 실제 IPC와 느린 systemctl 관측 adapter, large owned file tree

**동작:** 동시 bounded read RPC·status refresh·reconcile을 실행하고 event-loop delay를 기록한다.

**관측해야 할 결과:** diagnostic 작업의 동시성·queue가 bounded이며 RPC 지연과 stale 표시가 정의된 budget을 따른다.

**음성 대조군:** 동기 per-agent show를 hot dispatch에 복원하면 측정 oracle가 regression을 드러낸다.

**lane / 현재 실행 상태:** `stress` / `NOT_RUN`.
### V23B — cached observation은 authorization이 아님

**준비:** fresh/expired/foreign status snapshot과 그 뒤 바뀐 incarnation/cgroup

**동작:** diagnostic display와 실제 start/stop/auth를 각각 수행한다.

**관측해야 할 결과:** 표시는 observedAt/freshness를 반영하며 effect 경로는 별도 현재 권한/death proof를 재확인한다.

**음성 대조군:** cached inactive를 confirmDead 대체로 사용하는 control이 실패한다.

**lane / 현재 실행 상태:** `kernel` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

최적화 명목으로 relational validation 삭제, stale cache로 admission/authority/death 승인, unchecked .all 대량 적재를 새 캐시로 옮기기만 함, diagnostic failure를 valid empty로 표시하는 것을 금지한다.

## 6. 호환성·실패·롤백

C0/C1. public status wire shape는 유지하고 기존 schema로 표현할 수 없는 추가 관측은 internal view/diagnostic에 한정한다. budget 부족은 partial/unknown으로 표시한다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

측정된 개선과 명시한 상한이 있고 correctness-critical checks가 유지된다. 실제 unit 변경·incarnation 변경 직후 cached view가 권한이 되지 않는 시험이 통과한다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
