## 1. 이 작업이 필요한 이유와 판정의 강도

F06은 수동 설정 형식이 원래 보장하지 않는 bundle 원자성을 제품의 관리형 editor에 추가하는 작업이다. individual atomic rename를 bundle transaction이라고 부르지 않고 manifest를 한 commit point로 만든다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP13.01 — managed generation writer

D02의 layout을 구현하고 source snapshot에서 전체 후보를 준비한다. 각 generation의 private temp/relative path/durable parent 순서를 명시한다. role promptFile을 index-root 기준의 새 generation path로 rebase하고 effective source equivalence를 검사한다.

### WP13.02 — validation와 conflict fencing

실제 전체 config validator가 통과한 후보만 게시한다. 편집 시작 당시 source version과 현재 version이 다르면 덮어쓰지 않는다. host tenure로 OMA writer를 직렬화하고 외부 수동 편집과의 충돌도 감지해 거절한다.

### WP13.03 — commit 경계

모든 file/dir flush 후 manifest를 마지막에 교체하고 parent flush까지 끝나야 committed 결과를 반환한다. after-rename failure는 unconfirmed와 관측 가능한 target identity를 반환/보고한다. 기존 writer의 두 patchFile 호출은 제거한다.

### WP13.04 — migration·export

manual source를 읽어 managed generation으로 복제하고 manifest만 전환한다. old files는 rollback/export 근거로 보존한다. shared authored role 파일은 필요한 경우 profile별 사본으로 풀고 model/resources/capabilities 결과가 동일한지 검사한다.

### WP13.05 — retention 정책

제안 기본은 committed generation 최대16개, 관리형 config bytes 최대256MiB다. 실제 허용 fixture와 operator 요구를 확인해 D02에 수치를 확정한다. 이 제한은 config 편집 자원 한도이지 valid config 읽기를 제한하는 새 schema 규칙이 아니다. limit 초과는 편집 거절; 안전한 삭제는 quiescent GC로 한다.

### WP13.06 — 모든 writer 이관

settings/extensions/split utility가 기존 파일에 제자리 patch하는 경로를 남기지 않는다. 임시 compatibility shim은 호출자가 없는 것을 확인한 뒤 삭제한다.

## 4. 회귀 시험 — production 경로를 사용한다

### V13A — bundle commit의 원자적 visible generation

**준비:** 한 config에서 principal role/model/host revision이 함께 바뀌는 edit

**동작:** generation 파일 write/fsync, generation directory flush, manifest replace, manifest parent flush의 앞뒤에서 종료한다.

**관측해야 할 결과:** reopen 결과는 완전한 old 또는 complete new다. 어떤 케이스도 새 role+옛 revision 조합을 valid snapshot으로 반환하지 않는다.

**음성 대조군:** 기존 role-then-host 개별 replace를 복원하면 mixed-state oracle가 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V13B — legacy migration과 오래된 writer conflict

**준비:** inline/manual bundle·이미 존재하는 generations·stale Settings snapshot

**동작:** manual→managed 전환, 동시에 오래된 편집 요청, rollback export를 수행한다.

**관측해야 할 결과:** 원본 authored files를 덮어쓰지 않고 stale edit는 충돌로 거절한다. old reader compatibility와 old writer 금지가 구분된다.

**음성 대조군:** stale candidate를 unconditional last-write-wins로 저장하면 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V13C — retention이 live reader와 자원 한도를 함께 지킴

**준비:** old generation을 읽는 delayed process와 여러 committed generations

**동작:** 한도 도달 edit 및 quiescent GC를 수행한다.

**관측해야 할 결과:** live reader가 참조하는 generation은 삭제하지 않는다. 한도 초과는 explicit refusal이지 무제한 증가가 아니다. orphan temp만 구분해 정리한다.

**음성 대조군:** 나이만 보고 generation을 지우거나 root 전체 cleanup하는 control을 거절한다.

**lane / 현재 실행 상태:** `stress` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

symlink current pointer 도입, rename만 하고 fsync 생략, incomplete generation을 가장 최근 것으로 추정해 자동 선택, 오래된 renderer가 role 파일을 직접 수정하게 남김, 수동 config 원본 자동 flatten/삭제를 금지한다.

## 6. 호환성·실패·롤백

C2 authoring/layout 변경. wire/ledger schema는 유지한다. managed 승격 뒤 old writer downgrade는 지원하지 않는다. rollback은 검증된 이전 generation을 새 commit으로 선택하며 accepted intents는 보존한다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

reader-first→writer-switch 순서로 old/new fixture가 통과한다. crash matrix에서 구세대/신세대가 명확하고 혼합은 valid로 보이지 않는다. 관리형 모드의 retention·export·old writer 금지 정책이 문서화된다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.

## 8. 추가 구현 조건 — lost update와 자원 한도

[CONFIG-CONTRACT](../decisions/CONFIG-CONTRACT.md)의 critical section을 구현한다. expected-version 비교와 commit 사이에 또 다른 managed edit가 interleave되지 않게 해야 한다. host tenure 한 개를 공유하는 async handler 두 개도 별도 시험한다. 새 lock을 추가하는 대신 기존 owner의 단일 실행 방식으로 충분한지 먼저 확인한다.

16세대/256MiB는 미검증 제안값이다. 기존 valid input의 maximum closure, 중복 prompt 공유, 한 번의 old+new 준비 비용을 계산해 정상 설정의 최초 managed edit까지 불가능하게 만들지 않는지 확인한다. read compatibility를 제한하는 hidden schema constraint로 넣지 않는다. 실제 한도와 어떤 정상 profile에서 편집이 제한되는지는 D02에 확정하고 UI에 사전 표시한다.
