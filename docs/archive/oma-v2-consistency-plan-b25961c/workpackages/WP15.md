## 1. 이 작업이 필요한 이유와 판정의 강도

F07은 필드 하나의 bug이면서 UI가 policy를 무엇으로 이해하는지의 문제다. current config, stored agent spec, next engine snapshot, 현재 관측된 실행 상태를 분리해야 한다. Worker model의 다음 activation 읽기는 기존 정상 경로이므로 그것을 깨뜨려 일관성을 만들지 않는다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP15.01 — field 의미 확정

D05에 따라 Worker profile을 bootstrap seed 선택으로 명명하고 seed0/이미 bootstrap 완료 시 편집 가능성과 설명을 명시한다. childProfile 편집이나 기존 agent migration은 별도 기능으로 남긴다.

### WP15.02 — descriptor 연결

WP11 field descriptor가 label/value/apply-time/validation을 동시에 소유하게 한다. screen이 별도 apply-time 문자열을 다시 정의하지 않는다. config.max와 active population의 차이를 사용자에게 설명한다.

### WP15.03 — 저장·적용 결과

commit 성공, validation 성공, activation 적용 대기를 구분하는 narrow UI result를 사용한다. after-commit reload가 실패하면 성공한 generation identity와 관측 오류를 함께 표시하고 구세대 메모리 값을 현재처럼 표시하지 않는다.

### WP15.04 — profile/resource 경계

다음 activation에 읽을 모델·prompt·extensions와 accepted spec의 capability/resource identity를 구분한다. 이 차이는 WP25와 공동 검증한다. validator를 통과했다고 기존 durable spec을 overwrite하지 않는다.

### WP15.05 — 실행 상태 표시

engine의 actual model을 기존 pinned API로 관측할 수 있을 때만 현재라고 표시한다. 지원 API가 없으면 configured/pending/unknown으로 표시한다. 새로운 broker wire field를 UI 편의를 위해 임의 추가하지 않는다.

## 4. 회귀 시험 — production 경로를 사용한다

### V15A — bootstrap profile의 실제 적용 시점

**준비:** seed0/seed1/복수 seed, bootstrap 완료/미완료 society

**동작:** profile와 initial worker count를 편집하고 reload·새 activation을 수행한다.

**관측해야 할 결과:** seed0 no-op를 성공한 worker 정책 변경으로 표시하지 않는다. 이미 생성된 agent spec은 변하지 않고 UI의 apply-time이 실제와 같다.

**음성 대조군:** next-activation 라벨만 유지하거나 childProfile을 몰래 바꾸는 control은 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V15B — configured 모델과 실제 running 모델 구분

**준비:** Principal engine은 old profile로 실행, config는 new profile로 저장

**동작:** settings/dashboard 표시와 다음 session/Resident activation을 관측한다.

**관측해야 할 결과:** 현재 적용을 관측하지 못하면 configured/pending으로 표시한다. 다음 시작에서 선택한 snapshot만 적용된다.

**음성 대조군:** config 값을 현재 engine 모델로 그대로 표시하는 control이 실패한다.

**lane / 현재 실행 상태:** `fast` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

필드 선택이 no-op인데 saved로만 표시, initial count 편집으로 기존 worker 강제 생성/삭제, configured model을 observed로 표기, 모든 역할에 Principal profile fallback을 적용하는 것을 금지한다.

## 6. 호환성·실패·롤백

C1/C2 UX/authoring 의미 정리. 기존 bootstrap 데이터는 바꾸지 않는다. 사용자에게 이미 생성된 society의 seed 편집 효과가 없음을 명확히 알린다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

각 field의 실제 write 대상과 apply-time이 한 descriptor에 있고 seed/profile/model의 반례와 positive control이 통과한다. UI 문구와 runtime behavior가 같은 사실을 말한다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.

추가 읽기: [CONFIG-CONTRACT](../decisions/CONFIG-CONTRACT.md). partial authored source와 runnable validated snapshot을 구별한다.
