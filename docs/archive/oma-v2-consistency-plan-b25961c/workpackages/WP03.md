## 1. 이 작업이 필요한 이유와 판정의 강도

새 정적 확인 N02: broker는 custom --config를 받지만 Resident unit에는 전달 항목이 없다. H04: foreground child broker와 고정 broker.service dependency가 지원 환경에서 어떻게 결합되는지 별도 증명이 필요하다. 설정 generation과 delivery 개선이 정확해도 다른 프로세스가 다른 설정을 읽으면 전체 원칙은 깨진다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP03.01 — production launch graph 관측

각 entry의 인자·env·부모·unit·cgroup·private channel을 표로 기록한다. systemd-managed와 product-owned 경로를 구분하고 V03B를 수정 전에 실행한다. unit이 없는 clean account를 positive 환경으로 쓴다.

### WP03.02 — resolved launch location

기존 root/identity 검증을 재사용해 host에서 확정한 config locator와 root를 renderer까지 전달한다. renderer의 optional/default fallback으로 custom path를 버리지 않게 한다. secret이나 mutable authority를 단순 env 문자열로 옮기지 않는다.

### WP03.03 — mode-specific dependency 정정

D03에 따라 실제 존재하는 lifetime dependency만 render한다. Principal credential socketpair·host ancestry·singleton lease를 보존한다. BindsTo 삭제만으로 성공시키거나 systemd가 두 번째 broker를 띄우도록 하지 않는다.

### WP03.04 — effective unit 대조

rendered text뿐 아니라 실제 LoadState/FragmentPath/DropInPaths/ExecStart를 확인한다. worker profile resource 값과 실제 process가 읽는 config가 연결되는지 검증한다.

### WP03.05 — 지원 범위 문서화

실제 통과한 mode만 지원표에 포함한다. topology 가설이 해소되지 않으면 dependent kernel qualification을 blocked로 두고 다른 local WP는 계속한다.

## 4. 회귀 시험 — production 경로를 사용한다

### V03A — custom config와 XDG roots가 runner까지 일치

**준비:** 기본 config와 내용이 다른 외부 bundle, 공백/비ASCII path, 별도 XDG roots

**동작:** 실제 product launch→broker render→systemd Resident start를 수행한다.

**관측해야 할 결과:** broker/runner가 같은 config locator와 society/state/run roots를 사용하고 기본 파일로 조용히 fallback하지 않는다.

**음성 대조군:** unit argv에서 config locator 또는 root 전달을 제거하면 case가 실패한다.

**lane / 현재 실행 상태:** `kernel` / `NOT_RUN`.
### V03B — 깨끗한 계정에서 product-owned broker topology

**준비:** broker.service가 설치되지 않은 disposable user와 관리형 product mode

**동작:** 제품만으로 Resident를 생성·기동하고 broker/host 종료와 재기동을 관측한다.

**관측해야 할 결과:** 지원 mode는 실제로 실행되며 단일 writer/engine·stale fencing이 유지된다. 미지원이면 activation 전에 명시적 unsupported이지 가짜 READY가 아니다.

**음성 대조군:** 기존 개발 계정의 잔존 unit이 없으면 실패하는 fixture는 성공 증거로 인정하지 않는다.

**lane / 현재 실행 상태:** `kernel` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

auth cgroup 검사를 완화하거나 임의 PID를 Principal로 인정하는 해결, private credential의 file/env/argv 저장, clean environment 시험 없이 fixed service 의존성 제거를 금지한다.

## 6. 호환성·실패·롤백

C1(locator)/C2(topology). unit 교체는 disposable 환경에서 먼저 검증한다. live unit 재설치 전 기존 실행 quiescence와 rollback 가능한 rendered unit 사본을 확보한다. deployment mode 변경이 새 서비스/권한을 요구하면 ADR 확정 전 구현하지 않는다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

모든 지원 entry가 같은 launch contract를 사용하고 실제 mode별 lifecycle 시험이 연결된다. 단순 render unit test만 통과한 상태로 multi-agent runtime 지원 완료를 선언하지 않는다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
