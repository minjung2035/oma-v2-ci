## 1. 이 작업이 필요한 이유와 판정의 강도

원래 결함을 놓친 원인 중 하나는 개별 helper의 positive fixture가 전체 product-valid fixture로 해석되는 것이다. receipt라는 같은 단어를 쓰는 CLI cache test와 delivery evidence test도 구분해야 한다. crash exception과 process death, process death와 power loss의 차이를 검증 도구에 드러낸다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP02.01 — fixture 계층 분리

pure shape fixture, complete HostConfig fixture, live Store/Mail fixture, installed runtime fixture를 별도 이름으로 둔다. 정상 fixture 생성 결과는 실제 validator를 통과시킨다. corruption fixture는 명시적으로 그 경계를 우회한다.

### WP02.02 — 효과 counter와 독립 oracle

engine prompt, mail materialization, published ref CAS, DB acceptance, configuration pointer replace, unit start/stop을 test-side counter나 physical observation으로 기록한다. expected result를 production planner에서 그대로 계산하지 않는다.

### WP02.03 — checkpoint driver

기존 durable fault seam과 subprocess harness를 먼저 재사용한다. production이 test module을 import하지 않도록 한다. SIGKILL 테스트는 child가 실제 경계를 통과한 것을 parent에게 확인시킨 뒤 죽이고 새 process로 검증한다. 무제한 기다림을 금지한다.

### WP02.04 — failure matrix data

시험 명세를 phase와 expected preserved artifacts로 표현한다. checksum·inode·message manifest·incarnation·operation id를 함께 관측한다. 실패 후 실제 cleanups가 실행됐는지와 crash로 실행되지 않았는지 구분한다.

### WP02.05 — report 의미

파일 이름이 아닌 stable test ID와 source binding으로 결과를 남긴다. 새 테스트는 기존 lane과 local exclusion 정책에 넣고 skip/timeout/setup failure를 정상 실패 또는 blocked로 전파한다.

## 4. 회귀 시험 — production 경로를 사용한다

### V02A — 정상 fixture가 실제 loader를 통과함

**준비:** inline와 operations bundle, profiles/resources/limits를 production-valid 값으로 만드는 fixture

**동작:** readConfigurationSource뿐 아니라 loadConfiguration과 관련 composition까지 실행한다.

**관측해야 할 결과:** positive fixture가 실제 product loader를 통과하고 deliberate invalid fixture만 거절된다.

**음성 대조군:** 필수 quota/resource/model relation을 지운 fixture가 정상 fixture로 남으면 실패한다.

**lane / 현재 실행 상태:** `fast` / `NOT_RUN`.
### V02B — 실패 위치가 관측되는 crash driver

**준비:** 임시 파일/SQLite/Git와 별도 자식 프로세스; bounded sync barrier

**동작:** named checkpoint에서 child를 중지하고 parent가 종료한 뒤 새 process로 상태를 관측한다.

**관측해야 할 결과:** pre-effect/after-visible/after-durable/after-commit-before-response를 구분하고 hit되지 않은 checkpoint를 PASS로 집계하지 않는다.

**음성 대조군:** checkpoint가 실행되지 않은 dummy child 또는 cleanup이 실행되는 throw-only 경로로 교체하면 detection 실패로 표시한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V02C — 반례를 없앤 원본 복원이 시험을 깨뜨림

**준비:** 한 결함에 대한 production-linked regression과 부작용 counter

**동작:** 수정 전 동작을 임시 worktree에 복원해 같은 case를 실행한다.

**관측해야 할 결과:** regression은 실패하고 positive control은 정상적 검증 범위에서 동작한다.

**음성 대조군:** test oracle이 production decision helper를 그대로 호출해 자기 자신을 증명하면 거절한다.

**lane / 현재 실행 상태:** `property` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

product source에 global test bypass flag를 넣지 않는다. 임의 success mock으로 authority나 durability를 대체하지 않는다. 새 모델만 구현하고 그것을 실제 시스템과 비교하지 않은 채 regression 완료로 처리하지 않는다.

## 6. 호환성·실패·롤백

test/tooling C0. 기존 test case를 삭제하거나 environment 요구를 낮추지 않는다. fixture 정정으로 기존 시험이 깨지면 production validator를 느슨하게 바꾸기 전에 fixture 의미를 재검토한다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

WP05 이후가 재사용할 fixture/checkpoint API와 사용 예가 있고, driver 자체의 missing-checkpoint·timeout·false-positive 대조군이 통과한다. kernel/powercut 검증은 아직 별도다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
