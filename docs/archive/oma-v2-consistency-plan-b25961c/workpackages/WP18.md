## 1. 이 작업이 필요한 이유와 판정의 강도

ContextCoordinator에는 prepared wrapper와 별도 artifact settle이 있어 freezeObject/final observation/TX 실패의 자원 책임이 갈린다. 이 WP는 current authority와 candidate freezing을 보존하면서 전체 preaccept 수명을 scope에 연결한다.

## 2. 시작 전에 읽을 source와 변경 경계

- [S23](../guide/SOURCES.md#s23) — `src/git/context.ts`: 준비 scope와 acceptance 경계; 이전 동일 SHA 검토
- [S25](../guide/SOURCES.md#s25) — `src/git/submit.ts`: frozen spool·accepted effect·recovery; 이전 동일 SHA 검토

아래는 **검토·수정 가능한 후보 범위**다. 모두를 바꾸라는 뜻이 아니다. 실제 호출 관계를 확인한 후 필요한 최소 경로만 수정한다. 여기에 없는 production owner를 바꿔야 하면 구현 전에 범위·선행 작업·회귀 시험을 갱신한다.

읽을 작업 문서는 이 파일, [AI 실행 규율](../guide/AI-EXECUTION.md), [불변식](../guide/PRINCIPLES.md), 위 결정 문서다. 완료한 선행 작업의 handoff를 먼저 받아 현재 HEAD와 변화를 확인한다. 서로 다른 작업의 오래된 source 사본을 합치지 않는다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP18.01 — 현재 물리 순서 고정

stream validation→staged tree→candidate→mail object→acceptance→canonical effect의 순서를 test로 고정한다. 기존 에러 precedence를 변경할 때는 이유를 적고 규범과 대조한다.

### WP18.02 — tree 취득 등록

prepareContextStream이 만든 tree의 정확한 소유권을 scope에 넘긴다. preparation 내부 실패 cleanup과 scope cleanup이 같은 FD를 중복 닫거나 이미 다른 owner에 넘어간 tree를 지우지 않도록 한다.

### WP18.03 — 나머지 fallible 구간 포함

candidate generation, EML 생성, freezeObject, effects.current, policy/actor 재검증, accept transaction이 같은 preaccept disposition 결정 아래 있게 한다. 함수 일부에만 try/catch를 추가하는 방식으로 끝내지 않는다.

### WP18.04 — acceptance 이후 transfer

commit 성공 또는 불명에서 recovery 자료를 유지한다. operation plan이 참조한 tree/message만 해당 operation에 넘긴다. postaccept failure는 error phase/effect knowledge에 맞춰 unknown/repair로 남기고 preaccept cleanup으로 되돌리지 않는다.

### WP18.05 — 불필요 중복 제거

기존 prepared wrapper/discard 호출 중 scope와 중복되는 분기를 제거한다. semantic parser·FD-containment·final current-authority 검사 자체는 유지한다.

## 4. 회귀 시험 — production 경로를 사용한다

### V18A — context 모든 preaccept 실패 지점의 책임

**준비:** 실제 context entries/content와 Git preparation, frozen mail object

**동작:** prepare stream/candidate/buildEml/freezeObject/final current observation/accept transaction 앞뒤에서 실패한다.

**관측해야 할 결과:** 확실한 미수락·quiescent 자원은 정리된다. 수락/commit 불명 자료는 retained이며 이후 recovery가 원래 bytes를 사용한다.

**음성 대조군:** 기존 prepared helper 바깥 freezeObject와 current throw의 누수를 검출한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V18B — context 수락 후 연결 종료는 evidence를 지우지 않음

**준비:** accepted context plan과 staged tree, connection closed after acceptance

**동작:** 동일 키 retry와 context reconcile을 수행한다.

**관측해야 할 결과:** 새 candidate/새 payload를 만들지 않으며 frozen plan으로 기존 CAS/snapshot/notification이 수렴한다.

**음성 대조군:** 연결 cleanup에서 staging을 삭제하는 control이 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

실패 시 context tree 전체 무조건 삭제, request.expected를 current ref로 대체, candidate 재생성, context conflict를 silent retry, final auth/current check를 DRY로 제거하는 것을 금지한다.

## 6. 호환성·실패·롤백

C1. persisted context plan/path/hash recipe 불변. 이미 accepted된 context 자료의 retention 정책은 기존과 같고 filesystem corruption을 cleanup으로 숨기지 않는다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

preaccept의 모든 fallible 문장과 각 owned artifact가 실패 matrix에 연결된다. normal/recovery가 frozen candidate·bytes를 유지하고 별도 decision path를 보존한다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
