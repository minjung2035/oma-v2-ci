## 1. 이 작업이 필요한 이유와 판정의 강도

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP29.01 — 보장 문장 audit

"cannot", "guarantees", "always", "compile-time" 등에 해당하는 문장을 찾아 실제 enforce 지점/negative oracle를 연결한다. 증거가 없는 문장은 단정 대신 의도·한계로 정정하고 runtime 검증이 필요한 곳을 남긴다.

### WP29.02 — closed registry 수정

필수 field/method/kind의 union과 descriptor를 satisfies 또는 mapped type으로 연결한다. readonly/brand는 alias lifetime/프로세스 crash 후 one-use 보장이 아님을 명시한다. exported unsafe constructor/cast는 좁은 검증 boundary 안으로 제한한다.

### WP29.03 — static rule 정밀화

경계가 이동하면 실제 owner와 analysis scope를 바꾸고 broad allowlist를 추가하지 않는다. positive/direct violation/alias/false-positive 사례를 함께 둔다. 이미 TS compile이나 좁은 behavior 시험이 잡는 것을 별도 regex 규칙으로 중복 강제하지 않는다.

### WP29.04 — 시험 fixture 계층화

layout parser 시험, full config validity 시험, actual spawn 시험을 다른 proof scope로 적는다. 신규 behavior 회귀는 production 함수를 호출한다. 모형의 expected를 production helper에서 계산해 tautology로 만들지 않는다.

### WP29.05 — metadata와 문서 closure

owner/mutation map은 탐색과 누락 검사용이다. 실제 호출 경로·부정 oracle·fresh result가 있어야 proven이다. 신규 파일/requirement가 digest와 inventories에 들어가는지 검증하고 obsolete map/rule은 정확한 이유로 제거한다.

## 4. 회귀 시험 — production 경로를 사용한다

### V29A — static rule의 실제 보장

**준비:** 정상 source와 직접 위반·alias/import 변형·허용 유사 사례, 실제 TS Program

**동작:** 기존 architecture rule와 closed-key descriptor compile fixture를 수행한다.

**관측해야 할 결과:** 정해진 계약 위반은 잡고 허용된 경계는 거절하지 않는다. Record<string,...>를 닫힌 registry 보장으로 표시하지 않는다.

**음성 대조군:** 정상만 통과하거나 source 문자열 부재만 확인하는 control은 의미적 검증 증거가 될 수 없다.

**lane / 현재 실행 상태:** `fast` / `NOT_RUN`.
### V29B — fixture 계층과 proof 범위

**준비:** layout-only fixture와 production-valid config fixture, CLI cache와 delivery receipt 시험

**동작:** 각 시험이 호출하는 실제 owner와 asserted property를 분류한다.

**관측해야 할 결과:** 부분 loader 통과를 전체 config 시작 증거로, cache ordering을 delivery restart 증거로 확대하지 않는다. production-valid fixture는 실제 loader를 통과한다.

**음성 대조군:** 명칭만 같은 시험을 모든 requirement에 연결하는 control을 report validator가 거절한다.

**lane / 현재 실행 상태:** `fast` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

source 문자열 없음=정책 중복 불가능, branded type=one-use runtime 권한, test 이름 존재=proven, broad exception으로 checker 통과, fixture 오류를 production validation 완화로 해결하는 것을 금지한다.

## 6. 호환성·실패·롤백

C0/C1 tooling. 실제 파일 이름은 WP00 tree inventory로 확인한다. 예시 wildcard와 예상 metadata 파일이 없으면 만들어진 사실처럼 취급하지 말고 현재 equivalent owner를 찾아 연결한다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

각 보장 문장이 type/runtime/static/behavior/kernel 중 어디서 성립하는지 알 수 있다. 새 규칙의 positive·negative·우회·false-positive control이 있고 metadata는 실제 source와 동기화된다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
