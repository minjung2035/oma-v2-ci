## 1. 이 작업이 필요한 이유와 판정의 강도

N01: writeExclusiveFsyncedFile의 정상 경로는 파일 내용 fsync만 담당하고 parent flush는 caller 책임이다. receipt publisher는 final name 생성 후 그 flush를 명시하지 않는다. source-level gap이며 실제 power loss 손실을 이번에 재현한 것은 아니다. D01의 ReceiptDurable 의미를 먼저 실제 primitive와 맞춘다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP05.01 — publication contract 정의

encoded bytes와 receipt identity를 검증한 뒤 publication을 시작한다. event notification·session file 존재·receipt 파일 fsync·parent directory fsync의 의미를 구분한다.

### WP05.02 — private staged immutable publish

0600 temp를 held directory FD 아래에 생성하고 bounded bytes write→file fsync→no-replace final publication→검증→parent fsync를 구현한다. 기존 contained-fs primitive를 재사용하고 source/name을 재해석하는 window를 늘리지 않는다. 기존 immutable publisher의 0444 정책을 receipt에 적용하지 않는다.

### WP05.03 — EEXIST first fact

기존 최종 receipt를 같은 expected batch로 검증해 반환한다. 그 값을 무시하고 새 boundary를 completion evidence로 쓰지 않게 반환 계약을 문서화한다. conflict를 success나 absent로 바꾸지 않는다.

### WP05.04 — 실패 cleanup·unknown

temp만 자기 소유 identity로 정리한다. final publication 이후 flush 실패는 outcome uncertain이다. final receipt를 실패 처리 명목으로 삭제하지 않고 재관측/flush 가능성을 남긴다. process crash에서는 cleanup이 실행되지 않는 시험을 분리한다.

### WP05.05 — durability 증거

V05A/B를 먼저 통과시키고 실제 power-loss를 주장할 profile은 V05C까지 요구한다. API 이름만 Durable로 바꾸고 IO 순서를 그대로 두지 않는다.

## 4. 회귀 시험 — production 경로를 사용한다

### V05A — receipt 최종 이름의 durable publication

**준비:** 진짜 세션 fixture와 prepared batch, receipt parent가 이미 존재하는 경우 포함

**동작:** temp write/file fsync/final publication/parent fsync 각 경계에서 실패·process 종료를 주입한다.

**관측해야 할 결과:** 정상 반환은 검증된 complete receipt와 parent flush 이후에만 발생한다. final name이 partial bytes인 채 성공하지 않는다.

**음성 대조군:** parent flush 제거 또는 final name에 직접 쓰는 control을 syscall ordering/partial-file oracle이 검출한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V05B — receipt EEXIST와 private mode

**준비:** 같은 batch의 기존 유효 receipt 및 다른 identity의 receipt; 0600 parent policy

**동작:** publish를 반복하고 기존 name 충돌을 처리한다.

**관측해야 할 결과:** 최초 유효 receipt가 completion 기준으로 반환되고 bytes/identity는 덮어쓰지 않는다. receipt mode를 0444로 바꾸지 않는다.

**음성 대조군:** existing receipt를 새 boundary로 overwrite하거나 mode를 넓히는 control이 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V05C — power-loss claim 분리

**준비:** filesystem/VM 검증 가능한 disposable 환경과 동일 product publisher

**동작:** 정의된 durable 경계 전후에 VM/storage powercut lane을 수행한다.

**관측해야 할 결과:** 보고서가 process SIGKILL과 power-loss의 결과를 구분하고 실제 지원 FS 범위에만 durability를 주장한다.

**음성 대조군:** throw-only harness의 PASS를 powercut 증거로 집계하는 control을 거절한다.

**lane / 현재 실행 상태:** `powercut` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

기존 receipt를 atomic replace로 overwrite, 파일 mode 완화, partial final file을 유효로 채우기, parent fsync 없는 성공, temp glob 삭제, notification 수신만으로 session disk durability 선언을 금지한다.

## 6. 호환성·실패·롤백

C1, v1 receipt encoding 유지. 기존 손상 final receipt를 자동 삭제하지 않는다. publisher 개선은 미래의 partial publication을 막는 것이며 과거 손상을 임의 복원하지 않는다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

모든 receipt producer가 같은 publication 경계를 사용하고 반환 receipt가 authoritative first fact다. process crash 증거와 powercut 증거가 구분된다. powercut 환경이 없으면 그 요구는 BLOCKED이며 로컬 구현 완료와 분리한다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.

추가 읽기: [DELIVERY-CONTRACT](../decisions/DELIVERY-CONTRACT.md). 기존 identity 비교의 약화 없이 그 계약을 충족해야 한다.
