## 1. 이 작업이 필요한 이유와 판정의 강도

기존 architecture §7.3의 batch 재할당과 strict receipt 검증, 수동 bundle의 비원자성, product/systemd mode가 서로 다른 전제를 갖는다. 기존 규범에 덮어쓸 코드를 먼저 만들면 구조 개선 자체가 계약 drift가 된다. 이 WP는 제안의 기술 선택을 명문화하는 단계이며 운영 변경 권한을 획득하는 단계가 아니다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP01.01 — Fact/Relation/Phase/Authority 표 작성

delivery·config·preaccept·quota·lifecycle·Git·protocol별로 사실, authoritative store, derived view, 관계, 확정 시점, 현재 권한 검사를 적는다. 각 결정의 owner를 지정하되 모든 domain을 한 manager로 모으지 않는다.

### WP01.02 — D01–D06 확정

각 결정의 기본 선택을 source와 대조하고 기존 requirement ID의 충돌을 정정한다. v1 해법이 가능한데 schema를 새로 만들지 않는다. 불가능하다는 증거가 나오면 C3를 작은 별도 승인 항목으로 격리하고 관련 WP를 blocked로 둔다.

### WP01.03 — 지원 profile와 증거 수준 분리

foreground product, systemd-managed, confined, explicit unconfined, provider 없는 fixture, actual provider를 구분한다. 지원 명세와 release evidence를 혼동하지 않는다. 특히 actual systemd로만 판단할 topology는 WP03의 결과를 ADR의 필수 입력으로 둔다.

### WP01.04 — change surface와 registry 계약

새 primitive의 이름보다 owner와 입출력의 의미를 먼저 고정한다. public method registry, durable codec, resource descriptor, source-owner maps를 바꿀 필요가 있는 항목을 표시한다. 여러 registry를 없애기 위해 wire/DB 개념을 섞지 않는다.

### WP01.05 — 작업 순서 잠금

DEPENDENCIES와 compatibility gate를 확인하고 당장 구현 가능한 C0/C1와 계약 결정 이후 가능한 C2를 나눈다. 판단 보류를 승인으로 취급하지 않는다.

## 4. 회귀 시험 — production 경로를 사용한다

### V01A — 결정표의 완전성

**준비:** D01–D06과 현재 architecture/spec의 관련 요구 ID

**동작:** 각 의미 충돌을 existing rule/제안 rule/승인 필요 사항으로 대조한다.

**관측해야 할 결과:** 모든 proposed behavior에 owning WP·검증 oracle·호환성 분류가 있다.

**음성 대조군:** 표에서 unknown/미수락 불명/legacy mismatch 행을 제거하면 review가 실패한다.

**lane / 현재 실행 상태:** `fast` / `NOT_RUN`.
### V01B — 범위 밖 계약 보존

**준비:** 현재 DB/wire enum·recipe·OPEN gate·rootfs opt-out·cost-accounting 범위

**동작:** 계획의 proposed types/states를 실제 durable schema와 비교한다.

**관측해야 할 결과:** 개념 state가 새 DB enum으로 자동 승격되지 않고 기존 지원 제한이 명시된다.

**음성 대조군:** 범용 성공/자동 재시도 규칙으로 intentionally unsupported를 제거한 변경은 거절한다.

**lane / 현재 실행 상태:** `fast` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

“일관성을 위해”라는 말만으로 public 권한·receipt identity·data retention·동봉 engine 책임을 바꾸지 않는다. 타입 브랜드나 새로운 class 목록을 ADR의 대체물로 삼지 않는다.

## 6. 호환성·실패·롤백

문서/계약 결정 C0–C2 단계다. irreversible migration을 실행하지 않는다. 결정 revert는 아직 영속 데이터를 바꾸지 않았을 때만 단순 문서 revert다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

D01–D06이 승인된 기술 결정 또는 explicit gate로 기록되고, 모든 WP가 따라야 할 충돌 해결 순서가 확정된다. 소스와 규범이 아직 다르면 그 차이를 named blocker로 남긴다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.

## 8. Runtime gate와 선행 순환 방지

WP01에서 runtime-dependent 결과를 미리 PASS로 만들지 않는다. D03은 기술 방향과 반드시 유지할 불변식만 잠그고 WP03이 실제 환경 결론을 채운다. 이것은 WP01→WP03→WP01의 실행 의존 순환이 아니다. WP03 결과가 기본안을 반증하면 ADR을 새 revision으로 갱신하고 affected WP를 재평가한다. C3 변경은 기본 선택의 실패만으로 자동 승인되지 않는다.
