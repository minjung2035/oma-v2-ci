## 1. 이 작업이 필요한 이유와 판정의 강도

F03/Q01: writer가 loader의 전체 제약을 실행하지 않고 PLACEMENT는 string-indexed map이라 주석의 exhaustiveness를 보장하지 못한다. 기존 validator를 또 복사하는 대신 순수 validation boundary와 편집 descriptor를 재사용한다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP11.01 — validator를 순수 경계로 공개

파일을 읽는 loadConfiguration과 전체 object를 검사하는 validateConfig를 분리한다. 기존 오류 의미·closed field·숫자·capability·quota relation을 그대로 유지한다. writer도 같은 validator를 호출하도록 한다.

### WP11.02 — ValidatedCandidate의 생성 경로

검증된 deep snapshot을 생성하는 좁은 함수만 두고 writer가 이 결과를 받게 한다. ordinary HostConfigV1 타입을 validation 완료 사실로 오인하지 않는다. 기존 호출자의 반환 타입 호환을 유지하는 얇은 facade는 허용하되 validator의 두 독립 구현을 남기지 않는다.

### WP11.03 — 편집 descriptor 단일화

EditableField는 실제 editable keys의 닫힌 집합이다. field별 value validation·pure transform·placement·apply-time metadata를 연결하고 compiler가 누락을 검출하게 한다. UI-only link field와 editable field를 구분한다. generic string key로 fallback하지 않는다.

### WP11.04 — validate-before-write

apply→전체 후보 validate→commit이라는 순서를 entry/setField 경로에 연결한다. 값 하나의 min/max뿐 아니라 lineage/seed/profile 관계를 검사한다. invalid이면 아무 파일도 바꾸지 않는다.

### WP11.05 — immutable identity 보존

UI 변경이 기존 agent spec/accepted plan/requestHash를 rewrite하지 않도록 한다. 새 config snapshot의 내부 identity는 기존 persisted hash recipe와 분리한다. map lookup은 own key로 검사하고 null-prototype map 정책을 보존한다.

## 4. 회귀 시험 — production 경로를 사용한다

### V11A — 유효하지 않은 편집은 저장 전 거절

**준비:** production-valid config; lineage=4/society=8, seed가 있는 변형

**동작:** worker limit를 lineage/seed 아래로 변경하고 initial seed count를 상한 위로 변경한다.

**관측해야 할 결과:** inline/split 모두 원본 file hashes가 불변이고 기존 loadConfiguration이 다시 성공한다. 오류는 해당 교차 제약을 설명한다.

**음성 대조군:** 기존 applyField→write→reload 순서를 복원하면 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V11B — field placement 완전성은 실제 compiler가 보장

**준비:** 새 EditableField의 닫힌 union과 field descriptor registry

**동작:** field를 하나 추가하고 placement/apply/display 정책 하나를 제거한 compile-only fixture를 실행한다.

**관측해야 할 결과:** 누락은 type error이며 일반 valid descriptor는 통과한다. Record<string,...>가 이를 대신하지 않는다.

**음성 대조군:** Record<string,...>로 완화한 control이 missing-field fixture를 통과하면 oracle가 regression을 검출해야 한다.

**lane / 현재 실행 상태:** `fast` / `NOT_RUN`.
### V11C — snapshot의 타입·실제 validator·immutable copy 연결

**준비:** 원본 plain config object와 prototype-sensitive map key, deep arrays

**동작:** validated snapshot 생성 후 원본을 바꾸고 편집을 수행한다.

**관측해야 할 결과:** snapshot과 accepted frozen specs는 바뀌지 않고 map membership은 own key로 판단한다. 기존 허용 ID는 호환성을 유지한다.

**음성 대조군:** shallow freeze/cast-only snapshot으로 바꾸면 relation 시험이 실패한다.

**lane / 현재 실행 상태:** `property` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

새 validator 복사, 저장 후 reload 실패를 validation으로 부르기, `as ValidatedCandidate`만 추가, 느슨한 Record<string> exhaustiveness 주장, child delegation을 worker-profile 편집의 부작용으로 바꾸는 것을 금지한다.

## 6. 호환성·실패·롤백

C0/C1. HostConfigV1 wire/authoring schema 자체는 바꾸지 않는다. 기존 valid config가 새로운 강한 validator로 갑자기 invalid가 되는 경우 fixture·규범을 먼저 검토한다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

모든 설정 write 경로는 전체 후보 validator를 지나며 invalid edit의 무변경 oracle가 통과한다. UI descriptor와 storage placement의 누락은 컴파일에서 발견된다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.

추가 읽기: [CONFIG-CONTRACT](../decisions/CONFIG-CONTRACT.md). partial authored source와 runnable validated snapshot을 구별한다.
