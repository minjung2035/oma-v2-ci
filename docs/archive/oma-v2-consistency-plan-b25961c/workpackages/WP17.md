## 1. 이 작업이 필요한 이유와 판정의 강도

F09는 helper가 없어서가 아니라 helper를 빠짐없이 호출해야만 맞는 구조다. 기존 PreacceptOwner를 바탕으로 자원을 취득한 즉시 cleanup 책임이 등록되게 한다. 다만 native 작업이 계속 접근할 수 있는 자원은 미수락이라도 삭제할 수 없다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP17.01 — scope API

`withPreacceptScope`/`PreacceptScope` 중 기존 스타일에 맞는 좁은 구현을 택한다. acquire의 성공 직후 실제 inode/FD/tree identity와 owning operation reference를 등록하고, 다음 fallible 작업 전에 등록을 끝낸다. 모든 effect를 추상화하는 범용 resource manager는 만들지 않는다.

### WP17.02 — disposition 상태

unaccepted-known/accepted-referenced/accepted-unreferenced/outcome-unknown/cleanup-unconfirmed를 구분한다. 결과 불명에서 deletion을 허용하지 않는다. linked creation처럼 row는 존재하지만 해당 artifact를 소유하지 않는 경우를 관계로 확인한다.

### WP17.03 — native preparation 관계

준비 subprocess가 끝나지 않았거나 arbitrary descendants가 불명일 때 tree를 지우지 않는다. PreparationExecutor와 shutdown barrier의 sticky uncertainty를 보존한다. DB rollback만으로 native effect가 종료됐다고 가정하지 않는다.

### WP17.04 — 정리의 완전성

cleanup 하나가 실패해도 다른 자기 소유 자원을 정리 시도하고 모든 원인을 aggregate한다. identity를 잃었거나 삭제 실패한 자원은 cleaned로 기록하지 않는다. 반복 settle/release는 idempotent하되 한 번 release한 proof로 새 ownership을 만들지 않는다.

### WP17.05 — 정리와 보존의 관측

test-side artifact inventory가 무엇을 retained/discarded/unconfirmed로 판단했는지 남긴다. production의 broad filesystem scan/GC를 새로 만들지 않는다. process crash로 실행되지 않은 cleanup은 recovery 정책의 입력이다.

## 4. 회귀 시험 — production 경로를 사용한다

### V17A — preaccept scope의 전체 자원 정리

**준비:** 파일·tree·bundle 자원을 둘 이상 소유한 scope와 실패하는 하나의 cleanup

**동작:** 수락 거절/DB 관측 불명/일부 cleanup 실패를 각각 일으킨다.

**관측해야 할 결과:** 확실한 미수락이고 소유 identity가 확인된 자원만 삭제한다. 하나의 cleanup 실패에도 나머지를 시도하며 primary error를 보존한다. 불명은 retain이다.

**음성 대조군:** 첫 cleanup throw로 나머지를 생략하거나 DB error를 false로 바꾸면 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V17B — linked acceptance가 orphan artifact 소유권은 아님

**준비:** operation은 accepted지만 plan이 해당 initialMessage를 참조하지 않는 linked-create fixture

**동작:** scope를 settle한다.

**관측해야 할 결과:** accepted row 존재 여부뿐 아니라 해당 artifact의 실제 reference relation을 보고 정확한 미소유 artifact만 정리한다.

**음성 대조군:** getOperation(id)!=null 하나만으로 모든 artifact를 보존하거나 삭제하는 control이 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

accepted 여부를 catch→false, unconditional finally deletion, operation row 존재만으로 모든 artifact 소유 판정, tree glob cleanup, native uncertainty에서 삭제, identity 없는 삭제 성공 기록을 금지한다.

## 6. 호환성·실패·롤백

C0/C1. 새로운 durable journal/table을 기본으로 추가하지 않는다. scope는 기존 authoritative operation plan과 artifact identity를 사용한다. crash 이후 없는 메모리를 복구 증거로 사용하지 않는다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

scope 자체가 불확실성·부분 실패·linked acceptance를 정확하게 처리한다. 아직 caller가 모두 이관됐다고 주장하지 않고 WP18–20에 이관 API와 예외 처리 규약을 넘긴다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
