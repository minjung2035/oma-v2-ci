## 1. 이 작업이 필요한 이유와 판정의 강도

Store는 schema version을 거절하기 전에 WAL 관련 쓰기 PRAGMA를 적용한다. 거절할 파일도 바뀔 수 있고, constructor 중간 throw에서 handle 정리 책임을 명확히 해야 한다. 이 작업은 SQLite writer를 늘리는 것이 아니라 existing single-writer open의 순서를 바로잡는다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP04.01 — open 단계 분리

path identity·existing/new 판정·호환성 preflight·writer setup·migration·reader/transition composition을 구분한다. unsupported DB를 접수하기 전에 쓰기·자동 recovery가 일어나지 않는 native open 옵션과 supported SQLite 동작을 확인한다.

### WP04.02 — read-only preflight와 sidecar

unknown DB를 immutable=true로 무작정 열어 WAL을 무시하지 않는다. read-only WAL 조건과 hot journal 복구 요구를 확인하고 안전한 판독이 불가능하면 refused/unavailable로 남긴다. sidecar를 삭제해 문제를 해결하지 않는다.

### WP04.03 — constructor 실패 cleanup

DatabaseSync 생성 직후부터 handle 소유를 명시하고 모든 후속 throw에서 닫는다. lifetime에 Store를 넘기기 전과 후의 소유권을 구분한다. migration 실패는 primary error와 rollback/close failure의 원인을 보존한다.

### WP04.04 — 기존 transaction 보존

scope active/owner/thenable 검사와 cross-row 검증을 그대로 연결한다. unsupported version의 읽기 거절을 이유로 valid-v1 decoder를 완화하지 않는다.

### WP04.05 — 새 DB·기존 DB 대조

fresh creation, v1 existing, unknown version, corrupt header, busy lock, read-only filesystem, WAL sidecar 존재/부재 각각의 결과를 기록한다.

## 4. 회귀 시험 — production 경로를 사용한다

### V04A — unsupported DB refusal가 파일 상태를 바꾸지 않음

**준비:** 닫힌 unsupported user_version DB, DELETE와 WAL 각각; WAL/SHM/journal inventory

**동작:** Store opening을 시도하고 실패 후 파일 bytes·journal_mode·sidecar 생성과 descriptor를 관측한다.

**관측해야 할 결과:** 지원되지 않는 schema를 쓰기 PRAGMA/자동 복구/DDL 전에 거절한다. 지원 DB와 fresh DB는 정상 open된다.

**음성 대조군:** 기존 순서대로 WAL을 먼저 적용하면 시험이 실패해야 한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V04B — 생성자 중간 실패에서 DB/lock 수명 보존

**준비:** new DB와 supported DB, migration/PRAGMA/reader 구성의 실패 seam

**동작:** 각 단계 실패 후 새 writer 획득과 descriptor baseline을 검사한다.

**관측해야 할 결과:** 소유 DB handle은 닫히며 transaction 불명 상태는 증거 보존한다. unrelated lock을 풀지 않는다.

**음성 대조군:** constructor error에 close를 생략한 control이 FD/lock oracle에 걸린다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

unknown DB의 header만 믿고 auto-migration, WAL sidecar 삭제, `immutable` 옵션으로 active WAL 무시, SQLite transaction을 async 함수로 변경하는 것을 금지한다.

## 6. 호환성·실패·롤백

C1. schema 변경 없음. read-only refusal의 범위는 SQLite sidecar 동작까지 포함해 문서화한다. old code revert로 writer PRAGMA 문제가 되살아날 수 있으므로 운영 데이터에 downgrade 전 검증한다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

unsupported refusal의 무변경 범위와 예외가 명시되고 supported-v1/new DB baseline이 유지된다. handle/resource cleanup 시험이 실제 Store import 경로에서 통과한다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
