## 1. 이 작업이 필요한 이유와 판정의 강도

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP08.01 — tick action 분기

prepare 결과와 evidence observer를 사용해 settle-only/deliver/observe/repair를 명시적으로 분기한다. `inFlight`는 여전히 동시 tick을 억제한다. 실패한 batch map이 evidence phase를 대신하지 않게 한다.

### WP08.02 — settle 우선

valid receipt가 있으면 engine busy 확인보다 settlement 의미를 먼저 검토한다. live host endpoint의 현재 인증이 없으면 명시적으로 보류하거나 broker-owned startup recovery에 넘긴다. session offline을 권한 없는 complete의 근거로 만들지 않는다.

### WP08.03 — first receipt 기준

publishDeliveryReceipt의 반환값을 받아 completion evidence를 만든다. 최초 boundary가 durable해진 뒤 새로운 engine/session 정보를 덧붙이지 않는다. complete의 응답이 유실된 경우도 exact replay로 끝낸다.

### WP08.04 — backoff와 분류

session claim 경쟁, provider failure, completion I/O, corrupt receipt를 구분해 처리한다. BATCH_CONFLICT라는 error code만 보고 모든 문제를 단순 session 경쟁으로 축약하지 않도록 발생 phase를 함께 사용한다. failedAt 보관도 active/recoverable 범위와 명시 한도로 제한한다.

### WP08.05 — 중복 알림과 tool 효과의 차이

증거가 확정되지 않은 알림의 재전달은 기존 정책을 따르되 tool mutation은 frozen same-key 의미를 유지한다. domain contract보다 강한 exactly-once 성공 문구를 UI에 쓰지 않는다.

## 4. 회귀 시험 — production 경로를 사용한다

### V08A — Principal complete만 재시도

**준비:** host가 소유한 session, prepared batch, 정상 boundary; complete 첫 호출을 반영 전 실패

**동작:** tick을 다시 수행한다.

**관측해야 할 결과:** session.deliver는 총 1회, receipt publication은 최초 fact 유지, complete는 재시도된다.

**음성 대조군:** receipt 조회 없이 deliverOne부터 시작하는 control이 counter assertion에서 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V08B — session이 바뀌거나 busy여도 역사적 정산 의미 유지

**준비:** durable receipt는 옛 sessionPath, 새 engine 또는 busy session; 정상 host 권한

**동작:** 정산 후보를 처리한다.

**관측해야 할 결과:** 새 모델 turn을 시작하지 않으며 최초 receipt sessionPath로 complete한다. 권한이 아직 없으면 명시적 보류 후 trusted recovery로 처리한다.

**음성 대조군:** 기존 receipt 반환값을 버리고 새 sessionPath를 complete에 쓰면 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

engine를 매번 재시작해 중복을 숨기거나 receipt 존재만 확인해 내용 검증 생략, complete failure→새 request key, mode flag로 모든 host auth bypass, arbitrary stale batch를 자동 완료하는 것을 금지한다.

## 6. 호환성·실패·롤백

C1. existing prepared/completed·receipt format 유지. 원래 영수증을 보존하므로 이미 완료한 engine 효과를 rollback하거나 재실행하지 않는다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

engine delivery count와 completion attempt count가 서로 구분되고, receipt 이후의 재시도는 실제 source에서 settle-only다. sessionPath 변경·busy·응답 유실에도 최초 증거 의미가 유지된다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
