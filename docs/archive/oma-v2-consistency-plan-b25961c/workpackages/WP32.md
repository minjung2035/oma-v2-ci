## 1. 이 작업이 필요한 이유와 판정의 강도

본 계획이 모든 파일을 작업에 배정하는 것과 실제 모든 파일을 검토·검증하는 것은 다르다. 최종 단계는 이 차이를 강제한다. 문서의 "구조 개선 종료"나 과거 test count가 미래 구현을 검증하지 않는다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP32.01 — coverage 전수 closure

REVIEW-COVERAGE의 모든 production 경로를 실제 변경 후 파일과 대조한다. 유지한 파일도 어떤 관계를 검사했고 왜 안 바꿨는지 기록한다. 새 파일·삭제 파일·nonmanifest contract/scripts/tests까지 WP00 diff inventory로 추가한다. unread 경로가 남으면 전수 완료라고 하지 않는다.

### WP32.02 — 불변식 전체 대조

12개 INV 각각에 authoritative definition, mutation owner, evidence/phase, dependent consumers, actual regression을 연결한다. 동일 정책의 독립 복사본은 제거·생성/동등성 고정·정당한 경계로 분류한다. 예외는 범위와 이유를 적고 암묵적 fallback으로 남기지 않는다.

### WP32.03 — 문서 수렴

architecture/spec/physical-ordering의 승인된 의미를 동기화한다. managed/manual config, current/history identity, normal/recovery, product/systemd topology, zero-config naming과 opt-out 범위를 명시한다. HANDOFF에는 현재 재개점만 두고 과거 수치를 누적하지 않는다.

### WP32.04 — fresh evidence 마감

RUNBOOK대로 original inventory drift를 먼저 관측하고 generator는 실제 실행한다. 최신 source digest에 모든 필요 입력이 포함됐는지 확인한다. final docs 변경이 digest를 바꾸면 그 영향 범위를 다시 검증하고 기록한다. CI는 push 뒤 해당 run에서 읽는다.

### WP32.05 — 승인과 미완료 분리

EXIT-CRITERIA를 판정한다. 코드 완성/로컬 검증/실제 runtime qualification을 구별한다. 남은 BLOCKED가 있으면 release-approved라고 쓰지 않는다. 최종 보고는 이번 범위에서 얻은 보장과 남은 한계이며 10점·무결함 보증이 아니다.

## 4. 회귀 시험 — production 경로를 사용한다

### V32A — 전수 검토와 요구-구현-시험 closure

**준비:** WP00 고정 Git tree, 현재 production inventory와 추가 계약/scripts/test tree, 모든 handoff

**동작:** 각 실제 파일/불변식/변경 항목에 read status·owner·구현·시험·evidence를 대조한다.

**관측해야 할 결과:** SCOPE_ONLY가 검토 완료로 둔갑하지 않으며 누락 파일/미닫힌 required decision/NOT_RUN release lane이 최종 승인에서 검출된다.

**음성 대조군:** 파일을 WP에 배정하기만 하고 REVIEWED/PROVEN으로 표시하면 실패한다.

**lane / 현재 실행 상태:** `fast` / `NOT_RUN`.
### V32B — 최종 source와 CI 결과의 결박

**준비:** 정확한 최종 commit과 working-tree input digest, 로컬 raw 결과, 해당 SHA의 실제 CI run

**동작:** 생성 전 baseline 보존·재생성·검증 후 SHA/digest/runs를 대조한다.

**관측해야 할 결과:** 과거 성공 수·다른 merge/head·실행 전 문서가 현재 증거로 쓰이지 않는다. 실패 CI 원인이 없으면 알 수 없다고 기록한다.

**음성 대조군:** skip/미실행/부재 로그를 PASS로 바꾸거나 current-SHA CI 값을 commit 전에 미리 확정하면 실패한다.

**lane / 현재 실행 상태:** `fast` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

생성 숫자 수동 수정, proof 없이 PROVEN 표시, unread file을 문제 없음으로 채움, old CI 성공 재사용, 원시 로그 없는 실패 원인 추정, 기존 열린 spike를 문서에서 삭제해 release를 통과시키는 것을 금지한다.

## 6. 호환성·실패·롤백

C0 문서/검증. 규범 변경은 이미 승인한 ADR 범위만 반영한다. branch protection, CI 실행/변경, PR/merge/push 등 외부 write는 사용자의 명시적 허용 범위를 지킨다. 영속 자료 rollback은 COMPATIBILITY 정책을 적용한다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

모든 required WP/ADR/파일 검토/회귀/지원 환경이 상태와 증거를 갖는다. 검증되지 않은 보장은 별도로 남고, 최종 출처가 정확한 commit과 입력 bytes에 연결된다. 최종 릴리스 승인은 필요한 환경별 gates를 통과했을 때만 가능하다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
