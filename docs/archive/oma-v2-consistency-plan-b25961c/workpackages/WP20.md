## 1. 이 작업이 필요한 이유와 판정의 강도

Submit은 비교적 잘 정리된 preaccept 처리를 이미 갖고 있다. 새 scope를 도입했다고 정상 경로를 전면 재작성하지 않는다. Mail/submit/create/context의 같은 소유권 규칙을 연결하되 서로 다른 physical publication decision은 유지한다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP20.01 — 기존 보장 characterization

mail ID/date/EML hash와 logical recipients/frozen recipients를 비교한다. submit은 exact candidate/exportRef/prerequisites/bundle과 operation id를 고정한다. 같은 operation retry가 다른 데이터를 만들지 않는 시험을 먼저 유지한다.

### WP20.02 — scope 이관 최소화

이미 안전한 cleanPreaccept/settleByAcceptance를 새 scope로 옮길 때 behavior delta를 최소화한다. spool과 mail object의 ownership transfer가 서로 독립된 조건인지 확인한다. 사용하지 않는 wrapper를 추가하지 않는다.

### WP20.03 — materialization 권한

Git publication proof가 필요한 result/context mail을 일반 mail path로 우회하지 않는다. accepted artifact는 immutable primitive, inbox/world views는 derived replace를 사용한다.

### WP20.04 — error와 cleanup 연결

postaccept import/publish/mail settle 실패를 phase/effect knowledge에 맞게 분류한다. primary corruption을 secondary cleanup ENOSPC가 가리지 않도록 한다. 실제 owned temp cleanup 실패를 성공으로 숨기지 않는다.

### WP20.05 — 전체 coverage closure

mail/submit 하위 파일을 REVIEW-COVERAGE에 따라 줄별로 검토하고 유지/수정 근거를 남긴다. 발견하지 않은 결함을 만들기 위해 refactor하지 않는다. 다른 domain에 복사된 ID/EML recipe가 없는지 producer/consumer 관계로 확인한다.

## 4. 회귀 시험 — production 경로를 사용한다

### V20A — mail/submit same-key와 scope transfer

**준비:** 실제 MailModule/SubmitCoordinator/RequestCache와 bundle·EML

**동작:** 수락 전후 connection loss, concurrent same-key와 published-ref 재관측을 수행한다.

**관측해야 할 결과:** frozen EML의 ID/date/hash/recipient snapshot과 bundle bytes가 보존되고 물리 publication·quota 소비가 중복되지 않는다.

**음성 대조군:** retry에서 현재 HEAD/recipient set/EML date를 재생성하는 control이 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V20B — immutable publication과 derived view 복구 분리

**준비:** accepted mail object는 정상이나 mailbox/archive derived link만 누락된 상태

**동작:** reconcile과 view 재생성을 실행한다.

**관측해야 할 결과:** authoritative object를 보존하며 derived view만 재생성한다. view 존재만으로 operation success를 기록하지 않는다.

**음성 대조군:** derived overwrite primitive를 accepted object에 적용하거나 EEXIST를 검사 없이 success로 처리하면 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

accepted EML/bundle 재생성, recipient snapshot 재확장, immutable object를 generic replace로 갱신, all errors retryable, named artifact 없이 staging glob GC, generic workflow로 normal/recovery 통합을 금지한다.

## 6. 호환성·실패·롤백

C0/C1. mail wire/RFC/persisted byte recipe를 바꾸지 않는다. immutable objects와 canonical refs의 retention은 코드 정리 이유로 줄이지 않는다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

네 mutation family의 preaccept disposition이 일관되고 실제 bytes·refs·rows 회귀가 유지된다. 새 scope의 caller 이관이 끝나면 obsolete helper를 제거하고 독립 정책 복사본이 남지 않았음을 기록한다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
