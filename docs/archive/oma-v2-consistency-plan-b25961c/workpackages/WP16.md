## 1. 이 작업이 필요한 이유와 판정의 강도

F04는 basename slug가 storage identity로 쓰이는 충돌이다. 이 문제를 고칠 때 stateRoot가 바뀌면 lease/accepted paths/receipt 경로도 영향받는다. first-run provisioning의 실패 관측과 신규 repo 게시도 같은 fact/phase 규칙으로 검토한다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP16.01 — identity 함수

entry에서 정규 real project path를 관측하고 pure 함수가 D05의 bounded slug+digest를 생성하게 한다. 전체32자 문법을 지키며 canonical source binding을 별도 검증한다. display name과 authority locator를 구분한다.

### WP16.02 — legacy 선택·mismatch

기존 slug state를 자동 이동하지 않는다. source binding을 확인할 수 없거나 다른 프로젝트면 mutation 전에 명시적으로 거절/안내한다. read-only control panel을 제공할 경우에도 기존 society의 source를 정확히 표시한다. intentional migration은 별도 승인이다.

### WP16.03 — 초기 binding publication

binding metadata의 version·mode·max bytes·fsync·backup 범위를 문서화하고 정확히 그 source를 seed에 사용한다. 명시 config.society 불일치와 binding 불일치를 같은 default fallback으로 해결하지 않는다.

### WP16.04 — provision 관측 분리

projectHead/hasCanonicalMain에서 absent와 Git observation error를 구분한다. existing broken repo를 없는 repo로 취급해 초기화하지 않는다. staged bare repo와 canonical seed의 file/dir durability를 검사하고 최종 이름 publish 전에 가능한 준비를 완료한다.

### WP16.05 — rootfs와 소유권

tenure를 얻지 않은 실행은 config/provision/repair를 하지 않는다. trusted rootfs repair는 owned mode에만 있고 source binding 변경의 부작용으로 host의 다른 tree를 고치지 않는다. accepted paths가 있는 stateRoot는 단순 rename하지 않는다.

## 4. 회귀 시험 — production 경로를 사용한다

### V16A — 서로 다른 프로젝트의 기본 identity 분리

**준비:** 동일 basename/비ASCII/32자 이후 차이/정규화 충돌의 두 임시 Git repo

**동작:** 각 프로젝트에서 기본 society를 유도하고 provisioning한다.

**관측해야 할 결과:** 서로 다른 canonical source는 서로 다른 society가 되고 full binding 검증으로 digest 충돌도 덮어쓰지 않는다. 동일 realpath 별칭은 같은 identity를 선택한다.

**음성 대조군:** basename만 사용하는 control이 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V16B — 기존 society와 초기화 실패 보존

**준비:** legacy slug society·existing canonical main·source binding mismatch·partial staged repo

**동작:** 재실행과 명시 society 선택·기동 실패를 수행한다.

**관측해야 할 결과:** 기존 canonical main을 새 project로 reseed하지 않는다. mismatch/partial state를 자동 빈 repo로 대체하지 않으며 loser가 state를 수정하지 않는다.

**음성 대조군:** exists만 보고 정상으로 간주하거나 실패를 no-HEAD로 바꿔 seedEmptyRoot하는 control이 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

legacy society 자동 rename, 다른 프로젝트 HEAD로 existing main 이동, source read failure를 빈 프로젝트로 처리, 동일 digest 충돌에서 덮어쓰기, no-tenure 과정에서 rootfs 수정하는 것을 금지한다.

## 6. 호환성·실패·롤백

C2. 새 기본 이름은 새 society에 적용한다. 기존 상태 이전은 accepted absolute locators 때문에 별도 migration 계획 없이는 하지 않는다. 명시적인 operator source 변경과 일반 실행을 구분한다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

first-run identity와 저장 binding이 일치하며 동명 프로젝트가 다른 society로 분리된다. 기존 society와 interrupted provisioning을 source-preserving 방식으로 처리한다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
