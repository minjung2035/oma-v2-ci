## 1. 이 작업이 필요한 이유와 판정의 강도

H01과 F10은 한 문제의 두 면이다. 입력을 받았다는 UI 사실, stdin에 썼다는 transport 사실, engine가 accepted했다는 사실, run이 settled됐다는 사실이 분리돼야 한다. timeout 또는 일반 종료 통지가 그 상태들을 지워서는 안 된다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP09.01 — prompt 상태 모델

queued/dispatching/accepted/settled/refused/unconfirmed/returned의 실제 필요한 구분을 정의한다. 이것은 새 durable entity가 아니라 session-local 상태다. 각 prompt는 stable sequence와 session generation에 묶고 text의 반환 여부를 기록한다.

### WP09.02 — claim-before-write 유지

Human·delivery 모두 write 전 synchronous claim을 유지한다. command 명시 거절은 안전하게 release할 수 있지만 write/accept 결과 불명은 release하지 않는다. engine run이 여전히 가능하면 기다리거나 정확히 소유한 child를 종료하고 확인하는 정책을 사용한다.

### WP09.03 — late event 귀속

observer closure를 해당 session generation에 묶고 unsubscribe를 수명과 함께 정리한다. Pi가 실제로 제공하지 않는 correlation id를 있다고 가정하지 않는다. run id 없는 이벤트를 처리할 때 한 generation의 outstanding run을 하나로 제한한다.

### WP09.04 — 종료와 입력 반환

미전송 waiting을 순서대로 onPromptFailed/새 명시 결과로 돌려준다. 전송됐으나 수락 불명인 text는 unconfirmed로 별도 표시하고 자동 재전송하지 않는다. onEnd와 close가 중복 호출돼도 반환은 한 번이다.

### WP09.05 — 표시와 데이터 소유권

UI draft 복원과 engine send 상태를 분리하고 텍스트가 공개 로그·receipt에 들어가지 않게 한다. process 자체 SIGKILL 후 메모리 draft 보존을 새로 보장하지 않는다. durable drafts가 필요하면 별도 private retention 설계다.

## 4. 회귀 시험 — production 경로를 사용한다

### V09A — 수락 응답 불명에서 소유권 유지

**준비:** 실제 PrincipalSession과 제어된 Pi RPC peer; delivery prompt bytes는 전송됨

**동작:** 수락 응답을 지연시키고 accept deadline·Human 대기 입력·늦은 settle을 순서대로 발생시킨다.

**관측해야 할 결과:** 명시 거절 또는 owned run 종료/settle 확인 전 Human 입력을 새 run으로 넘기지 않는다. ambiguous timeout은 busy 해제의 증거가 아니다.

**음성 대조군:** timeout finally에서 unconditional release하는 control이 ownership assertion에서 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V09B — 엔진 종료 시 미전송 Human 입력 복원

**준비:** busy session에 세 Human prompt, 그중 하나 unanswered인 상태

**동작:** transport close/error/명시 quit를 각각 발생시킨다.

**관측해야 할 결과:** written-but-unknown과 never-written을 구별한다. never-written 입력은 순서대로 정확히 한 번 반환된다. 종료 통지만으로 큐를 버리지 않는다.

**음성 대조군:** waiting을 비우지 않고 session 참조만 버리거나 전부 자동 resend하는 control이 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.
### V09C — 중복·늦은 event가 새 owner를 해제하지 않음

**준비:** 동일 process 안에 session generation 전환, 늦은 error/settled callback

**동작:** 옛 callback을 새 session 생성 뒤 전달한다.

**관측해야 할 결과:** 그 callback은 옛 owner만 종료하고 새 Human/delivery claim은 유지한다. 이벤트가 run id를 안 주면 없는 상관관계를 지어내지 않는다.

**음성 대조군:** 전역 bool busy만으로 상태를 덮어쓰는 control이 실패한다.

**lane / 현재 실행 상태:** `property` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

accept timeout→free, 모든 오류→미전송, broker restart→queued Human 자동 resend, 가짜 agent_settled event, private prompt를 world/status 로그로 노출하는 처리를 금지한다.

## 6. 호환성·실패·롤백

C1 internal session state. wire/DB 변화 없음. 대기 입력을 반환하는 UX 변화는 WP28에서 검증한다. 이전 버전으로 rollback할 때 미전송 큐의 메모리 상태는 자동 이전되지 않으므로 종료 전 사용자에게 반환한다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

불명인 실행을 종료한 것처럼 다루는 경로가 없어야 한다. 명시 거절·write 실패·응답 지연·engine 종료가 각각 다른 정확한 사용자 결과를 낸다. 새 session generation을 옛 callback이 해제하지 못한다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
