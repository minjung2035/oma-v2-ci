## 1. 이 작업이 필요한 이유와 판정의 강도

quota 숫자를 정확히 비교하는 것만으로 전체 소비가 bounded하지는 않는다. 스트림 예약, 실제 disk bytes, workspace write, completion 비용의 수명과 보장 수준을 구분해야 한다. 현재 tree scan은 외부 writer까지 통제하는 hard quota가 아니다.

## 3. 구현 순서 — 아래 소작업 단위로 커밋을 분리한다

### WP22.01 — accounting 모델

논리 예약과 물리 관측을 정의하고 이중계수/누락 조건을 표로 만든다. transport→operation handoff에서 보존할 예약 책임을 명시한다. hardlink/directory/symlink allocated bytes 계산과 safe-integer를 유지한다.

### WP22.02 — reservation lease

reserve/release를 opaque handle 수명으로 연결하고 repeated release는 idempotent하게 한다. 기존 연결 소멸이 accepted operation 책임을 지우지 않도록 handoff를 구체화한다. 모든 Promise rejection과 early return을 시험한다.

### WP22.03 — settlement headroom

D04의 범위에서 동시에 허용할 settlement 양과 최악 encoded metadata/DB transaction 비용을 측정한다. 고정 reserved bytes는 실제 SQLite/WAL 증가의 hard bound가 아님을 명시한다. 부족 시 보류·repair 안내를 하고 unlimited fallback을 두지 않는다.

### WP22.04 — admission 관측과 외부 writer

freshness가 불충분한 diagnostic cache로 admission을 허용하지 않는다. 외부 same-UID writer 때문에 hard bound를 보장할 수 없는 profile은 지원표에 한계를 표시한다. kernel quota를 주장하려면 별도 실제 profile evidence가 필요하다.

### WP22.05 — 자원 누수 시험

동시 stream/취소/slow reader/recovery에서 FD·reservation count·staging bytes·pending task 수의 상한과 정상 복귀를 측정한다. orphan evidence는 안전한 GC 정책 없이는 자동 삭제하지 않는다.

## 4. 회귀 시험 — production 경로를 사용한다

### V22A — 예약·실제 bytes·소유권 이관

**준비:** 동시에 열리는 bounded stream 두 개, 실제 spool과 accepted artifact

**동작:** declare/reserve/write/handoff/connection close/TX unknown/settle를 조합한다.

**관측해야 할 결과:** 예약을 이중 release하지 않으며 전송 bytes가 accepted bytes가 됐다고 accounting에서 사라지지 않는다. overflow와 reserve exhaustion을 명시 거절한다.

**음성 대조군:** handoff 시 예약을 먼저 잃거나 total을 두 번 빼는 control이 실패한다.

**lane / 현재 실행 상태:** `stress` / `NOT_RUN`.
### V22B — settlement reserve와 실제 ENOSPC

**준비:** admission cap에 도달한 state, bounded settlement demand, 별도 실제 full FS fixture

**동작:** new work와 completion/cleanup을 각각 시도한다.

**관측해야 할 결과:** 논리 quota refusal와 physical exhaustion을 구분하고 완료 불명 evidence를 보존한다. reserve를 hard cap 보장으로 광고하지 않는다.

**음성 대조군:** full FS를 catch→completed 또는 unlimited reserve로 바꾸는 control이 실패한다.

**lane / 현재 실행 상태:** `durable` / `NOT_RUN`.

시험 ID는 이 계획의 새 ID다. 같은 이름의 test 파일이 이미 존재한다고 가정하지 않는다. 기존 시험이 동일 계약을 검증하면 중복 파일 대신 확장하고, [테스트 원장](../verification/TEST-CATALOG.md)에 실제 파일·case 이름을 연결한다. 모형만 통과한 결과는 production 통합 증거가 아니다.

## 5. 금지하는 해결법

전체 tree scan 제거 후 stale cache만 신뢰, host filesystem hard quota를 구현했다고 주장, receipt 정산에 무제한 allowance, arithmetic overflow 무시, accepted artifact를 quota 회수를 위해 삭제하는 것을 금지한다.

## 6. 호환성·실패·롤백

C1/C2 resource policy. 새로운 비용 회계나 usage entity 의미를 추가하지 않는다. reserve 도입은 지원 profile별로 검증하고 기존 quota를 조용히 무시하지 않는다.

작업 중간에 실행 자료가 없으면 `BLOCKED` 또는 `NOT_RUN`으로 기록한다. 코드 revert는 영속 상태 rollback과 같지 않다. DB·receipt·configuration generation을 바꾼 뒤 과거 바이너리를 재실행하려면 [호환성 표](../guide/COMPATIBILITY.md)를 먼저 적용한다.

## 7. 완료 판정과 다음 AI에게 넘길 것

reservation과 artifact 수명이 일치하고 논리 quota·실제 ENOSPC·외부 writer 한계가 명확하다. 부하 시험이 실제 원인별로 failure를 분리한다.

공통 필수 증거: 변경 전후 HEAD와 input digest, 변경 파일, Fact/Relation/Phase, 실제 시험 명령·종료 코드·skip 수, 원본으로 되돌렸을 때 깨지는 회귀 시험, 남은 미검증 범위. [handoff 양식](../templates/HANDOFF.md)을 채운다. `npm run typecheck`, `npm run build`, 관련 시험을 통과한 뒤 해당 commit의 architecture/inventory 상태를 확인한다. 정확한 종합 순서는 [검증 실행 규율](../verification/RUNBOOK.md)을 따른다.
